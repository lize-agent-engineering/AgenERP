## 一、结论摘要

**十条承重假设：4 条成立、3 条部分成立、2 条不成立、1 条问题确认但解法未验证。**

没有任何一条的结论是「架构方向错了」。但有**三条**如果留到建设中才发现，会造成返工：

| | 若不验证会怎样 |
|---|---|
| **定制包 `git revert` 撤不掉** | P2 的核心验收标准做到一半才发现不可达，而它是项目对外最有说服力的演示 |
| **洞察 Agent 自由巡检找不到业务荒谬** | P1 验收标准写的是「无需指令即能报出积压 1,010 米」——实测做不到，会在演示前爆炸 |
| **解释 Agent 会过早收敛** | 它复现了本项目**存在的理由**（那个 ERPNext 原生误读），且给出的建议会造成实际业务损失 |

## 三、五个最有价值的发现

### 1. 解释 Agent 复现了本项目要修的那个错误

受约束 Agent 对 `SAL-ORD-2026-00001` **只调一次 `doc.get` 就下结论**：

> 还有 10 Meter 未出库交付……还有 188 元未开票……需要针对剩余数量创建/提交 Delivery Note。

每个数字都对，业务结论完全错——那 10 米是 `LOSS-00003` 已审批的合理损耗，**补发是错误操作**。
这正是 `ARCHITECTURE.md` 附录 A #2 记录的、本项目存在的理由之一。

根因不是模型不行，而是**循环里没有「证据够不够」的判据**。模型停下时手上的证据自洽，
没有任何内部信号提示还差一层没看。

→ 修法遵循项目自己的第一条设计公理（护栏长在执行路径上，不写在提示词里）：加一条
**确定性的循环门禁**——问题点名了某张单据，就必须先追溯它的血缘才允许作答。
加上之后同一模型同一道题给出了与完整 harness 一致的正确结论。

### 2. `permission.scope` 把越权提问的成本砍掉 97%

Spike 01 曾记录：权限受限的用户问超纲问题，模型工具调用量从 7 次放大到 **35 次**——
它在系统性地寻找绕过路径。这既烧钱，在审计视角下又是越权探测特征。

补上 `permission.scope` 后，同一道题：**1 次调用**，$0.043，26 秒。

> 熔断是兜底，`permission.scope` 是正解。

因此该工具已从「可选工具」升级为**由控制循环在会话开场自动注入**。

### 3. 定制包能 diff、能 apply、能迁移，就是撤不回来

用架构文档自己的例子（给外协收货加水洗牢度字段）跑完六步，卡在最后一步：

**从定制包里删掉字段、再 sync，站点上的字段纹丝不动。**

原因在 Frappe 的 `sync_customizations_for_doctype` —— 它是**纯 upsert，没有任何删除分支**。

而「可 revert」是 §1.4.4「防死亡螺旋」的**全部理由**，也是与低代码平台的根本分歧所在。

→ AgenERP 必须自建三个部件：规范化器（导出物含 `modified`/`creation`，不改也产生 diff）、
**差集 apply 引擎**（revert 的唯一实现路径）、`schema.drift` 巡检（删字段留孤儿列）。
建议随 P0 一起做——它们与契约层、状态快照是同一批地基。

### 4. 洞察 Agent 找得到「逾期」，找不到「荒谬」

开放式指令「你自己找异常」，Agent 找到了应收逾期 ¥18,612、应付逾期 ¥2,200（都对、都有用），
**漏掉了成品仓积压 1,010 米 / ¥6,450**，并主动把该区域判为「✅ 正常」，依据是达成率 100%。

两类异常的可发现性根本不同：

| | 逾期账款 | 积压 1,010 米 |
|---|---|---|
| 异常在哪 | **一个字段上**（`status = "Overdue"`） | **不在任何字段上** |
| 前提 | 会查即可 | **必须先知道「产出远大于销出」是个问题** |

`achievement_rate = 100%` 是绿的，GL 借贷平的，负库存 0，每张单都合规——**没有一个字段是红的**。

> **「无需指令」成立，「无需规则」不成立。**

这给了行业包一个不可替代的存在理由。Spike 01 曾把行业包大幅收窄（schema 已表达的语义不必重复），
一度让人怀疑它可有可无；本次补上了另一半：**schema 能表达「是什么」，表达不了「什么样算不对」。**

### 5. 结构化导航打赢了语义检索

在 9,776 个字段上做向量检索，最好一档 Top-5 只有 75%。失败方式高度统一——
**语义对了，单据错了**：「发票还有多少没收回来」返回 `Purchase Invoice` 的字段，
「总账借方金额」返回 `Journal Entry.total_debit`。ERPNext 里 `qty`/`warehouse`/`debit`
在几十个 DocType 上重复出现，字段级 embedding 天然分不开「哪一张单」。

**而受约束 Agent 四道探针全部通过，全程没有用到任何向量检索。**
它用的是 `system.overview` → `meta.fields` → `doc.links`。

→ ERP 的 schema 是强结构的，把它压平成向量再用相似度找回来是自找的信息损失。
§8.1 的向量索引已降级为兜底召回，P1 的交付改为把结构化导航工具做扎实——**减少 P1 工作量**。

## 四、两个几乎被漏掉的陷阱

这两条都是在实验过程中撞出来的，不在任何原始假设里，但都会直接导致 Agent 给出错误答案。

### ① 「只看已提交单据」会把行业知识整类丢掉

强化门禁时写了一条看似稳妥的规则：「`doc.links` 查出的**已提交**下游单据必须逐张打开」。
它对关键探针无效，因为：

```
Loss Review LOSS-00003   docstatus=草稿   可提交=False   ← 决定性的那张
```

**`Loss Review` 是不可提交的 DocType，docstatus 恒为 0。** 而 ERPNext 里承载业务判断的
自定义 DocType 大多不可提交：`Loss Review`、`Production Issue`、`Pattern`、`Sample Order`……
**这是一整类，不是个例。**

→ 下游筛选必须是「排除已取消」，不能是「只要已提交」；`doc.links` 必须返回 `is_submittable`。

### ② 从权限表反推权限会漏报，而漏报比噪声危险

`permission.scope` 第一版从 `DocPerm` / `Custom DocPerm` 表反推，**漏掉了 `Sales Invoice`**
——而该用户明明读得到。权限的最终判定包含角色、Custom DocPerm 覆盖、User Permission、
共享、if_owner 等多重来源，只有框架自己说了算。

**噪声只是浪费 token；漏报会让 Agent 错误地拒绝回答。**

→ 必须逐个调 `frappe.has_permission`。且它对部分 Single DocType **抛异常而非返回 False**
（`System Health Report` 在 `load_from_db` 里调 `frappe.only_for`），必须 try/except 兜住。

## 五、未排除的残余风险

**这一节比前面几节重要。以下每一条都还是真的未知。**

| 风险 | 为什么没排除 | 建议何时排除 |
|---|---|---|
| **写权限下的注入** | 抗注入结论是在 **L0 只读** Agent 上得到的。操作 Agent 拿到写工具后，同样载荷的后果完全不同 | **P3 之前必须重测** |
| **Memory 投毒**（§8.4） | 本轮无记忆层。持久化注入比单轮注入危险得多 | 随 Memory v0 |
| **跨站点迁移** | 未建第二站点，「可迁移」是从 upsert 幂等性**推断**的，不是实测 | P2 |
| **重估值链路的事务外副作用** | 倒填日期未真正触发 `Repost Item Valuation`，而那是最可能出现 enqueue 的地方 | P3 |
| **U8 的解法** | 只做了现状测量，`meta.permission` 尚未实现 | P4 |
| **统计显著性** | **所有 Agent 探针每题各跑 1 次。** 没有任何一条结论有统计意义 | P5 评测集 |
| **门禁规则的过拟合** | 证据充分性门禁是从失败样本反推的。规则本身通用，但通用性未在新题目上验证 | P1 |
| **确定性门禁能否补偿模型能力落差** | L1/L2 门禁在本地 14B 上**均未能救回**多跳探针；L3（两跳传递闭包）本轮未跑完。**不得声称门禁可替代模型能力** | P1 |
| **中间档模型** | 只测了前沿云模型与本地 14B。**最可能的生产配置（DeepSeek-V3 级 API、30B~70B 本地）完全没测** | P1 |
| **零依赖栈未真正启动** | 只验证到 `docker compose config` 解析通过 | P0 |
| **模型可能已在预训练中见过 ERPNext** | 无法排除。对所有基于开源 ERP 的 Agent 项目同样成立 | 系统性因素，不可排除 |

## 六、对路线图的净影响

### 新增工作量

| 项 | 归属 | 理由 |
|---|---|---|
| 定制包规范化器 + 差集 apply 引擎 | **P0**（原隐含在 P2） | 与契约层、快照同批地基；是 P2 验收标准可达的前提 |
| 零依赖启动 CI | **P0** | 最便宜的一项，守的是开源项目第一转化率 |
| 证据充分性门禁 | **P1** | 不做则解释 Agent 会给出造成实际损失的建议 |
| 行业包业务合理性规则（每条带 `test_case`） | **P1**（原含糊带过） | 洞察 Agent 的能力全部押在这上面 |
| 回滚前提回归测试 | **P3** | `rollback` 依赖 ERPNext 的实现细节而非承诺 |
| 写权限下的注入重测 | **P3** | 现有抗注入结论不覆盖写场景 |
| `schema.drift` 巡检 | **P2** | 孤儿列会随定制成本下降而加速累积 |

### 减少的工作量

| 项 | 变化 |
|---|---|
| Schema 元知识向量索引 | **P1 交付项 → P2 可选项**。结构化导航已被证明够用 |
| DeepSeek Harness | 从「可能必需」→ **纯增强**。内置纯 Python 循环的可行性已实测 |

### 验收标准从「靠感觉」改成「可机器判定」

| 原 | 改 |
|---|---|
| 老板首页「有结论和基准」 | **每个角色默认首页渲染元素 > 0，空壳工作台数为 0**（现状：`Home` 渲染 0 个链接，8 个空壳） |
| 洞察 Agent「无需指令即能报出积压」 | 声明规则后能报出，**且移除规则后能复现漏报**——证明是规则在起作用，不是碰巧 |
| 定制包「可 revert」 | 从包中删除 → apply → **字段真的消失** |
| 解释 Agent 正确率 | 正确率 **+ 单次解释成本上限**（基线 $0.252/题） |
