### D-14 · Skills：能力沉淀的落点，走构建期那扇门（与 D-10 合并）

| | |
|---|---|
| 决策 | 引入 **Skills** 作为「可累积能力」的唯一落点，其生命周期**走 D-10 的构建期路径**：起草落 DocType（可见、可改、**不生效**）→ 人审 → 进 git → 部署生效 |
| 依据 | 用户 2026-08-24：「确认 skills 在系统中的作用和拣选、管理机制……可以和 D-10 合并考虑」。查证：全仓无任何 skills 设计，"skill" 仅出现在竞品分析（Rebuild 有 Skills/工具/知识库/MCP）。**当前 Agent 能力全部硬编码在工具契约里，用户无法教它新东西** |
| 与既有三者划界 | **工具契约** = 能做什么原子动作（代码）；**行业包** = 什么算不对（阈值/预警规则）；**Memory** = 这家公司的事实；**Skills** = **怎么做一件事**（多步骤手法）。例：「达成率<98% 算异常」属行业包；「客户 A 不接受 2% 损耗」属 Memory；「月末结账怎么核对这七张表」属 Skill |
| 拣选：三道闸 | ① **权限闸**（后端 Frappe 判定：涉及的 DocType 当前用户读得到吗）② **角色闸**（角色×Agent 矩阵）③ 描述匹配（到这步才轮到模型，借 Claude Code 的渐进披露：只载 name+description，命中才载正文）。**①②必须在候选清单构造时过滤，不是载入后判断** —— 理由同 `permission.scope` 实测：让模型判权限，调用量放大约 5 倍且可能错误拒答 |
| 风险档：**派生不声明** | **一个 skill 的风险档 = 它调用的工具中最高的那一档。** 只编排只读工具即 L0；含一步 `doc.submit` 即整体走 L2 审批路径。**不允许 skill 自我声明风险等级** —— 否则「这步不用审批」写进 skill 就能绕开门禁 |
| 红线（比 Memory 更重） | **Skill 永远不能影响权限判定和风险等级。** Memory 是事实，Skill 是**指令**且可能带可执行代码，注入面更大 |
| 与 D-10 的关系 | Skills **让 D-10 那条抽象的构建期路径有了具体载体**。草稿态「不生效」即是闸：用户看得见、改得动、可讨论，但只有过了 PR 进 git 的才会被拣选器看见 |
| 代价（诚实记录） | 加一个 skill 要走 PR，**慢**。换来可 diff / 可回滚 / 可审计 |
| 翻案条件 | 若 PR 节奏被实测证明不可接受，翻案方式是**给 L0-only（纯只读编排）的 skill 开快车道**，而不是整体放宽 |

### D-15 · 规则能覆盖的流程不 Agent 化

| | |
|---|---|
| 原则 | **规则能够覆盖的流程不必强行 Agent 化。Agent 更适合复杂、模糊、需要模型动态控制执行的任务。** |
| 依据 | 用户 2026-08-24 明示，作为项目级原则 |
| 判别问句 | 面对任一环节先问：**「这一步的判断能不能写成确定性规则？」** 能写就写成规则；只有当输入模糊、路径不可预先枚举、或需要按中间结果动态改变后续动作时，才交给模型 |
| 它加固了已有的哪些决策 | **不是新方向，是把已经在做的事说明白**：① 证据充分性门禁 L1/L2/L3 是**确定性条件**而非提示词（§5.0 ①「长在循环里，不是提示词里」）；② D-10 选行为 DSL 而非运行期编码 Agent；③ 装载器、判定器、对账全是纯代码；④ 工具契约的前置/后置是声明式条件，不由模型裁量 |
| ⚠️ 对 P1 的具体后果（**可能改设计**） | **洞察 Agent 的「巡检」这一段，本质是纯规则执行。** 行业包若是声明式规则清单（P1.6 要求「每条带 `test_case`」），那么「按清单逐条查、命中即报」**是代码，不是 Agent**。模型真正不可替代的位置在**命中之后**：为什么会这样、要不要紧、该怎么办 —— 那才是模糊的。<br>→ P1.5 的措辞「洞察 Agent 按行业包规则清单巡检」应重估：**巡检器（规则引擎）与解释器（Agent）是两件东西**，混在一个「Agent」里会让规则的确定性被模型的随机性污染，且成本白花 |
| 与 §5.0 ② 的关系 | Spike 08 实测「自由巡检发现不了跨单据业务荒谬」，结论是「无需指令成立，无需规则不成立」。本原则把它推进一步：**既然非要规则不可，那规则本身就该由代码执行**，而不是把规则塞进提示词让模型代跑 |
| 反向边界（不许滥用） | 本原则**不是**「能写规则就一定不用模型」。自然语言问句的理解、多跳取数路径的选择、归因叙述的组织，这些**枚举不完**，强行规则化会退化成脆弱的关键词匹配。判据是**「路径能否预先枚举」**，不是「看起来复不复杂」 |
| 翻案条件 | 出现实测证据表明某处规则化的成本显著高于 Agent 化且质量不占优。**「写规则麻烦」不构成理由** |

### D-16 · 以本项目的实测为准

| | |
|---|---|
| 原则 | **凡涉及本项目的技术判断，以在本项目中实际跑出来的测试为准。** 外部基准、他人评测、厂商声明、以及本仓早先在**别的数据集上**得出的结论，都只能作为**假设的来源**，不能作为**结论的依据** |

| 与 D-9 的关系 | D-9 切的是**数据与环境**的纠缠，本条切的是**结论**的纠缠。**引用别处的研究可以，继承别处的结论不行** —— 后者会让本项目的判断建立在一个从未在这里验证过的地基上 |
| ⚠️ 反向边界 | 本条**不是**「别处的东西一概不看」。外部基准仍是**最有价值的假设来源**（省下大量试错），也仍应引用其出处。禁止的只是**跳过复验直接当结论用** |

### D-18 · P1.7 改为「记账但不拦截」

| | |
|---|---|
| 决策 | P1.7 由「**单次解释成本上限**」改为「**单次解释成本记账**」：每次 LLM 调用的 token **三项分开记**（prompt / completion / **reasoning**），可按一次解释汇总。**不设阈值、不拦截。** |
| 依据 | 用户 2026-08-24 明示「记账但不拦截」 |

| ⚠️ **不拦成本 ≠ 不拦失控** | 取消的是**成本阈值**，不是**失控保护**。单次解释的**工具调用轮数上限**仍须存在：一个陷入循环的 Agent 会无限调工具，那不是「贵」，是**坏**。两者的判据分开写，不许合并 |
| 保留了什么 | 记账本身是将来设限的前提。**先有数据，再谈阈值** —— 与 D-16「以本项目实测为准」同一条理路：没有本项目的成本分布就定阈值，定出来的是外部经验 |
| 翻案条件 | 出现实际的成本压力（账单、配额），或某类任务被观测到成本分布长尾严重。届时**用已记的账**定阈值，不再拍脑袋 |

| ⚠️ 代价照实记 | 多一个要运维的进程（起停、健康检查、日志、崩溃恢复）。零依赖启动门禁的判据面随之变宽 —— 新服务必须也能在「一个 AI 变量都不配」时起得来 |
| 翻案条件 | 出现实测证据表明 HTTP 边界导致不可接受的延迟或语义损失（例如需要事务性地跨越两侧）。**「进程内调用更方便」不构成理由** |

### D-21 · 换模型不能让行为完全不变，但已做到「不会悄悄变差」

| | |
|---|---|
| 问题 | 用户 2026-08-25 问：**「可以改成更换模型而系统行为不变吗？」** |
| 结论 | **完全不变做不到**，但项目已把**该不变的都做成了不变的**，且剩余的「变」有一道兜底：**要么答对，要么明确拒绝，不会悄悄答错** |
| **换模型不变的部分**（已实现） | ① **权限** —— 由 Frappe 判不由模型判（`permission.scope` 逐个调 `has_permission`）② **工具返回什么** —— 契约里写死裁剪规则（`must_keep` / `max_rows`），模型改不了 ③ **证据充分性门禁** —— L1/L2/L3 是**确定性条件不是提示词**，弱模型只会被反复挡回去，不会被放行 ④ **巡检器找到什么** —— 纯规则引擎、**零 LLM 调用**，换任何模型报出的 1,010 台一模一样 ⑤ **行业包规则** —— 声明式、确定性执行 |
| **必然变的部分** | 能不能答出来（P1.0 实测：同一道题 `qwen-plus` **0/3** vs `qwen3.6-plus` **3/3**）· 答案措辞 · 工具调用次数 · 成本（`qwen3.5-plus` 回一句话烧 3,411 reasoning token，`qwen3.8-max` 只要 298，**11 倍**）· **这些是模型判断力本身，能规则化的话就不需要模型了** |
| **兜底：不会悄悄变差** | `agenerp/routing/router.py` 的规矩逐字是「**能力不满足就明确失败，绝不静默降级**」。给 `qwen-plus` 派一个需要 `multi_hop` 的任务，它**直接 `RoutingError` 拒绝**，而不是跑出一个差答案。<br>→ **这是一种行为不变性**：不是「答案一样」，而是「**要么答对，要么明确说做不了**」。对 ERP 而言后者比前者重要 —— 一个悄悄错了的库存分析，比一个明说「我做不了」的系统危险得多 |
| 推论（值得记） | **越是把逻辑推进规则层，模型选择就越不重要。** P1.5 的巡检器是极端例子 —— 它的产出与用什么模型**完全无关**。这是 D-15 的直接收益，也给「往哪个方向投入」指了路：**想让系统更稳，就把更多判断规则化，而不是换更强的模型** |
| 对 D-20 的约束 | 模型配置界面**必须显示能力档案**（哪些任务这个模型做得了），而不只是一个模型名下拉框。否则用户换完不知道自己失去了什么能力 —— 而路由器会开始拒绝任务，用户却不知道为什么 |
| 翻案条件 | 若将来出现「能力声明可被自动探测」的低成本方法（今天 `multi_hop` 只能人填，见 §12.5 残余风险），这条的兜底可以更强 —— 但**不变性的上限不会改变** |

#### D-22.1 · 为什么 LangChain Deep Agents 也不适合**解释 Agent**（2026-08-25 追问）

| | |
|---|---|
| 决定性理由 | Deep Agents 文档写明有些东西**配置不掉**：「CANNOT Configure —— Core middleware removal（TodoList / **Filesystem** / SubAgent **always present**）」。即 `ls` / `read_file` / **`write_file`** / **`edit_file`** / `glob` / `grep` **一定在模型的工具面上，删不掉** |
| 为什么这对本项目致命 | 我们的工具面是**十个工具全只读、写操作函数数 0**，且 `tools_readonly.py` 的规矩逐字「**必须逐个调 `frappe.has_permission`**」。Deep Agents 塞进来的六个文件工具**打的是容器文件系统不是 Frappe** —— `has_permission` 根本不会被调到。一个刻意做成零写、逐调用验权的 ERP 工具面，会凭空多出**一条绕过权限模型的写通道**。<br>**这不是调参能解决的，文档写的是 CANNOT** |
| 次要理由 | ① 强制的 TodoList / SubAgent 用不上（解释是短程：一问 → 一个带证据的答）② 我们的证据充分性门禁要重做成 middleware，等于**重写已跑着的 666 行换零新增能力** ③ `langchain` + `langgraph` + `deepagents` 整个依赖树进 ERP 镜像（§3.3 已把镜像体积列为可感知成本）|
| ⚠️ 要更正的两点 | ① **Windows 那条反对意见对 Deep Agents 不成立** —— 它是纯 Python，不像 DeepSeek Harness 要平台 wheel。公平起见记下来。② **我们其实已经在用 harness，只是不在产品侧** —— 7×24 开发循环跑的是 `claude -p`，**Claude Code 本身就是 harness**。准确说法是「**产品 Agent 自研，开发循环用现成 harness**」，而这个分工恰好对：开发循环的领域**就是文件**，正是 Deep Agents 擅长的；解释 Agent 的领域是 **Frappe 的权限化数据**，文件工具在那里是负资产 |

#### D-22.2 · 真正的风险不是「选错框架」，是「接缝烂掉」（2026-08-25）

人提了一个更要紧的担心：**等 Agent、工具、环境、skills 越来越多，再定 harness 就晚了。**

**核查后的结论：切换成本不随 Agent 数量增长，它随「抽象有多像某个框架」增长。**

| 今天的接缝（2026-08-25 实测） | |
|---|---|
| agent 循环 | **只有一处**（`agenerp/explain/loop.py:362`）。洞察 Agent 是零 LLM 规则引擎，根本没有循环 |
| 工具执行 | `agenerp/tools/runtime.py` 是「**唯一咽喉**」 |
| 工具定义 | `ToolContract` **对象** —— 是数据，不是框架装饰器 → 换 harness 只需一个适配器，成本 **O(1) 不是 O(工具数)** |
| 模型调用 | 全走 `router.route()` |

**所以现在是最好切的位置，不是最差的。** 真正会让成本变成 O(N) 的只有一件事：**多出第二处手写 agent 循环**。

**已落判据**：`tests/gates/test_agent_seam_stays_swappable.py`（2026-08-25，两条：agent 循环只许一处 / `ChatAdapter` 只许在 `routing/` 内构造）。**已做诱饵验证** —— 放进违规文件 `2 failed`，拿掉 `2 passed`，不是空判据。

#### D-22.3 · 翻案触发条件（写死，不是「以后再说」）

**下列任一成立，即重开 harness 决策**：

1. **出现第二个需要多步规划的 Agent** —— 规划里的**编排 Agent** 一旦要做，就是它
2. **出现真实的 subagent 派生需求**（不是「听说能派生」，是有具体任务非派生不可）
3. **会话要跨天续跑**且状态必须存活进程重启

**重开时的首选形态不是推倒重来，而是分工**：解释 Agent 短程、要确定性门禁把关 → 自研循环更合适；编排 Agent 长程多步要分解 → 那时上 harness。**Deep Agents 支持把已编译的图注册成 subagent**，解释循环可以被包成一个 subagent 塞进编排器，而不是重写。

#### D-22.4 · 一个必须说清的判断：难的是 ERP 那一半，不是 agent 那一半

人担心「自己做不到那么复杂和成功，而且不简洁优雅」。**担心是合理的，但来源要放对位置。**

「自然语言操作整个 ERPNext」的真正瓶颈，本项目**已经实测过**：

> **U6 · schema 向量检索能找对字段 —— 不成立**（最好 Top-5 = 75%，Spike 07）

一千多个 DocType、上万个字段，用户说一句话要知道他指哪个 —— **四分之一找不对**。
**Deep Agents 对这个问题的贡献是零**：它给 `write_todos` / `task` / 六个文件工具，没有一个知道 `Stock Entry` 和 `Stock Reconciliation` 的区别。

**仓里的现成证据**：P1.5 的巡检器是目前最值钱的组件，它有**零次 LLM 调用** —— 1,010 台设备的问题是纯规则引擎报出来的。

→ **D-21 那条推论对 harness 同样成立**：越是把逻辑推进规则层和 ERP 层，用哪个 harness 就越不重要。

**六件 agent 基础设施的实际状态（2026-08-25 实测）**：权限 ✓（逐调用 `has_permission`）· 上下文 ✓（`agenerp/context/`）· 记忆 ✓（`context/session.py`，落 Frappe DocType）· 护栏 ✓（`explain/gate.py` L1/L2/L3）· HITL ✓（`apply.py` 风险分级 + Frappe Workflow）· **RAG / schema 检索 ✗ 没有**。
**唯一没做的那件，恰恰是唯一 harness 也帮不了的** —— 已立为 P2 头号技术风险。

### D-26 · `TIMEOUT = 30` 是测试便利值，不是产品承诺 —— 拆成两个预算

| | |
|---|---|
| loop 问的那一句（停机分支 A） | 「**30 秒这个数是判据的一部分（即『解释必须在 30 秒内回』是本产品的承诺），还是一个测试便利值？**」|
| 裁定（人 2026-08-26） | **是测试便利值。** 依据两条实读：① `DECISIONS.md` 与 `02-WBS.md` **从未承诺过任何解释延迟 SLO**（2026-08-26 全文 grep，零命中）② 那个数原本就摆在 `FORGED_SID` / `QUESTION` 这些**测试夹具中间，无注释、无决策条背书** |
| loop 查明的机制（本条据以成立） | 一轮 `gates-l2-live` 恰好发 **2 次**真解释；某次服务端墙钟越过 30 秒 ⇒ 客户端在 `recv_into` 抛 `TimeoutError`，判据红；**而服务端没坏** —— 它算完仍去写 `200`，因对端已断开抛 `BrokenPipeError`。**次数逐一对得上**：`758b7bc` 1 次 ↔ 1 failed，`82a144a` 2 次 ↔ 2 failed。同一 sha 判定步墙钟 **70s(红) → 33s(绿) → 23s(绿)** |
| **改法：拆成两个预算，不是把 30 调大** | `CHEAP_TIMEOUT = 30`（健康检查 / 404 / 401 / 400 —— **这些卡住就是真故障，短预算有判别力**）· `EXPLAIN_TIMEOUT = 180`（真解释，要等模型）。<br>⚠️ **为什么不调大单个值**：那会把便宜请求的预算一起放宽，等于**用一个真问题的判别力去换另一个真问题的稳定性**。**一个判据只测一件事** —— 这几条问的是「答案里的人对不对」，不是「答案多久回来」 |
| 哪几处用长预算（逐条判过，不是全局替换） | 用 `EXPLAIN_TIMEOUT`：真 sid 的解释调用、`echoes_the_sid` 循环里 `path == EXPLAIN_PATH` 的两条。**保持 `CHEAP_TIMEOUT`**：伪造 sid（被 **401** 挡下）、非法参数（被 **400** 挡下）—— **这两类根本到不了模型** |
| ⚠️ 本条**没有**解决什么 | **「为什么某一次会落到 30 秒之外」仍未查明**（loop 自己点明的那一格）。本改动让**正确性判据**不再被延迟长尾误判，**但长尾本身还在**。若将来要立延迟 SLO，那是**另一条独立判据**的事，不该由正确性判据顺带承担 |
| 翻案条件 | ① 出现「解释延迟」的产品承诺（那时 30 或别的数就成了判据的一部分，要单独立一条门禁）② 或长尾成因查明后表明 180 秒仍不够 —— 那说明问题不在预算，**不要再调大** |
