## 10. 视图 DSL 与渲染器

### 10.1 为什么需要 DSL

三条路的比较：

| 方案 | 成本 | 天花板 | 「每家不一样」 |
|---|---|---|---|
| A. 留在 Desk 改 Workspace | 最低 | 只能放链接/卡片/图表 | 未解决 |
| B. frappe-ui 手写页面 | 中 | 高 | **未解决**（每加一个视图要写代码） |
| **C. DSL + 渲染器 + LLM 生成** | 高（一次性） | 高 | **解决** |

C 让「UI 太不直观」和「每家公司流程不一致」变成同一个问题的同一个解。

### 10.2 v0 只支持五种块（只读）

| 块 | 用途 |
|---|---|
| `list` | 列表 + 筛选 + 排序 |
| `detail` | 单据明细 |
| `metric` | 数字卡，**必须支持基准与对比** |
| `chart` | 图表 |
| `explain` | **解释性文本块** —— 回答「为什么这单还是待出货」，Workspace 永远做不到 |

**写操作 v0 不做，全部留在 Desk。** 理由：业务管理端本来就只读，风险最低，而「看不懂」是当前最大痛点。

### 10.3 渲染器职责边界

- 渲染器**只负责画**，数据与权限全部走 Frappe API 由后端强制
- 前端权限只做提示（「你看不到这个，因为…」），**绝不做判定**
- 未支持的块/字段类型 → 落回 Desk

### 10.4 行为不可配置 —— 视图 DSL 之外的独立缺口

实测（`demo.localhost` / Frappe v16.31.0）：ERPNext 的**页面**能被无代码搭出来，**行为**不能。

| 用户想要的 | 载体 | 无代码？ |
|---|---|---|
| 菜单 | `Workspace` 记录（`parent_page` / `sequence_id` / `roles`） | ✅ |
| 新表、子表 | `DocType`（`custom:1`） | ✅ |
| 字段 | `Custom Field`，43 种 fieldtype 可选 | ✅ |
| 按钮 | `Button` fieldtype | ✅ 加得上 |
| **按钮点了干什么** | **Client Script / Workflow** | ❌ **要写 JS** |
| **校验、自动计算、跨单据联动** | **Server Script** | ❌ **要写 Python** |

原生的无代码行为通道只有四条：Workflow、Notification、Assignment Rule、Auto Repeat。校验、自动计算、按钮动作、跨单据联动都不在其中。

**附带发现**：`custom: 1` 的 DocType **绕过 developer_mode**（`frappe/core/doctype/doctype/doctype.py:331`）。站点 `developer_mode` 关闭时，形态 Agent 仍能在生产站点建整张新表 + 整套页面——但 `export_customizations` 要求 developer_mode（§11.1）。**能建，导不出**：L3 动作可以造出治理体系看不见的东西。这比 §11.1 的 revert 缺口更靠前一环，待 Spike 12 收口。

→ 对 §10.1 那张 A/B/C 表的补充：**即使接受 Workspace 的天花板，行为层仍然无解。** 视图 DSL 若只覆盖呈现，定制包就只治理了一半。对策见 §10.5。

### 10.5 行为层：不做运行期编码 Agent

Frappe 的 Server Script 并非任意代码执行——它跑在 RestrictedPython 沙箱里（`frappe/utils/safe_exec.py`）：`compile_restricted` + 自定义 `FrappeTransformer`（:133）、白名单全局、`UNSAFE_ATTRIBUTES` 封死帧/生成器/traceback 内省（:776）、`frappe.db.sql` 被换成只放行 `select`/`explain` 的 `read_sql`（:724）。且 `server_script_enabled` 默认关闭。

**但沙箱防的是越狱，不防在权限内做错事**——而后者才是 ERP 定制的主要死法。因此运行期不引入编码 Agent：

| | 编码 Agent | 行为 DSL |
|---|---|---|
| 表达力 | 高 | 覆盖大部分「防错」需求 |
| 可 diff / revert | ❌ 两段脚本的语义差不是文本差 | ✅ |
| 人批 L2/L3 时 | 人得读代码 | 读一句声明 |
| 注入面 | 大 | 枚举内 |
| **工程量** | **小** | **大（要写解释器）** |

诚实记录这个取舍的形状：**编码 Agent 是便宜的那条路。** 它与 §10.1 的 A/B/C 完全同构，而当时选了贵的 C。行为层若选便宜的，会让 C 的投入白费——视图可治理、行为不可治理，定制包只覆盖一半，§11 的承诺整体失效。

**构建期编码 Agent 另论**：面向 ① 系统管理端、产物进 git 走 PR 人审、不自动 apply 到运行时。这类工具已经存在（通用编码助手），**不属于 AgenERP 的交付范围**。要决策的只有运行期那一个。

**逃生舱**：Client Script 风险显著低于 Server Script——它跑在浏览器端，后端仍会再判权限与校验，改不了数据的合法性；代价是能篡改用户所见（→ §7.5）。**即便开放也只作为人工逃生舱：由人写、走 git，Agent 不生成。**

行为 DSL 的边界与最小动作词表需专门设计，**不早于 P2 跑通**——届时才有真实需求清单可反推动作词表。

## 13. 状态快照与评测

### 13.1 state-diff 判定

Agent 动作前后各打一次快照，客观判定「改对了没有」——不看轨迹像不像，看**状态是否变成预期的样子**。

现有 `runtime_snapshot()` 已是雏形，输出包括：GL 借贷与差额、负库存数、各 DocType 已提交数、毛利构成。需扩展为：任意时刻打快照 + 两快照 diff + 断言 DSL。

### 13.2 关键局限（必须写进文档，不能自欺）

实测案例：系统自制入库 1,000 米 + 外协收货 1,000 米 = 2,000 米，发货 990 米，成品仓结余 **1,010 米、价值 6,450 元**。

而所有自动化门禁**全部通过**：GL 借贷平衡 ✅、负库存 0 ✅、毛利与凭证差额 < ¥0.01 ✅。

> **state-diff 能保证账是平的，保证不了业务是对的。**

Agent 一旦自动推单据，犯的恰恰是这种错：**每一步都合规，合起来毫无道理**。

→ 因此评测必须有第二层：**行业包提供的业务合理性规则**（如「成品库存无对应订单且 > N 天 → 异常」）。这也是洞察 Agent 存在的意义。

**Spike 08 把这一条推进了一步：不只是 state-diff 保证不了，自由巡检的 LLM 也保证不了。**

给老板身份、34 个业务 DocType 只读权限、开放式指令「你自己找异常」，Agent 找到了
应收逾期 ¥18,612 与应付逾期 ¥2,200（都对、都有用），**但漏掉了 1,010 米积压**，
并主动把该区域判为「✅ 正常」，依据是 `achievement_rate = 100%`。

它同时诚实标注了「库存/Stock Entry 明细未逐条核对」。**它不是查错了，是不知道该去查。**

→ 结论：**1,010 米积压就是行业包规则的 test case #1。** 且 P1 的验收标准应写成可归因的形式：

> 行业包 v0 声明「成品库存无对应订单」规则后，洞察 Agent 无需指令即能报出该异常；
> **并且移除该规则后能复现漏报**——以此证明是规则在起作用，不是模型碰巧猜到。
