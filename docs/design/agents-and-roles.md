## 5. Agent 清单

六个 Agent，按风险从低到高。**风险等级不是标签，是执行路径。**

| Agent | 端 | 职责 | 典型指令 | 风险 |
|---|---|---|---|---|
| **解释 Agent**<br>Explainer | ② | 回答「为什么/怎么样」 | "这单为什么还是待出货？" | **L0** |
| **洞察 Agent**<br>Analyst | ② | **按行业包规则清单**巡检异常并顶到用户面前 | （无需用户指令，但**由规则驱动**）"成品仓积压 1,010 台无对应订单" | **L0** |
| **视图 Agent**<br>View Builder | ②③ | 自然语言 → 视图 DSL | "我要看每笔订单毛利，低于 50% 标红" | **L0–L1** |
| **操作 Agent**<br>Operator | ③ | 代办业务动作 | "把今天这三台机的报工录了" | **L2** |
| **形态 Agent**<br>Schema Builder | ① | 改系统形态 | "给外协收货加个'水洗牢度'字段" | **L3** |
| **编排 Agent**<br>Orchestrator | 全 | 意图路由、任务分解、调度上述 | — | 继承最高档 |

### 5.0 两条由 Spike 02 / 08 实测产出的硬约束

#### ① 解释 Agent：证据充分性门禁（长在循环里，不是提示词里）

> **命名消歧（同名不同义，引用时必须带限定词）**：本节的 **证据门禁 L1 / L2 / L3**
> 约束的是「什么时候允许停下来」；§9 的 **风险档 L0–L3** 约束的是「要不要人批」。
> 两套编号互不相干，全文不得只写「L3」而不指明是哪一套。

**证据门禁 L1 / L2 —— 由 Spike 02 实测产出（管深度）**

Spike 02 实测：受约束 Agent 对 `SAL-ORD-2026-00001` **只调一次 `doc.get` 就下结论**——
照着订单头上的「订 1,000、已发 990」直接答「还差 10 台未发，需要补发」。
每个数字都对，业务结论完全错：**它停在了第一层证据上**。

**它复现了本项目要修的那个 ERPNext 原生误读（附录 A #2）。**

模型停下时手上的证据是自洽的，没有任何内部信号提示「还差一层没看」。因此必须加一条
**确定性的、与模型无关的**循环门禁：

```
规则 L1：问题点名了某张单据 → 接受 answer 之前，必须已对它调用过 doc.links
规则 L2：doc.links 查出的已提交下游单据 → 必须逐张 doc.get 之后才能作答
违反：拒绝该 answer，回注强制续跑消息
```

L2 由 `qwen3:14b` 实测补出：它照 L1 调了 `doc.links`、**看到了那张下游单据却没打开它**，
于是得出与不查血缘时同样错误的结论。

> ⚠️ **推出 L1/L2 的那个案例已随 D-9 退役，规则本身没有。** Spike 02 / 08 跑在退役前的
> XM 数据集上，当时「少发的那一部分」有一张 XM 自建的 custom DocType 记着「已审批损耗」。
> 该表不再继承，**L1/L2 的措辞一个字未动**——失效的只是推出它们的那个案例。
> 数量骨架（1,000 / 990 / 1,010）在恒锐动力数据集里原样保留，单位由「米」改为「台」。

**证据门禁 L3 —— 由 P1.0 入口关口实验设计（管覆盖）**

恒锐动力（户用储能电池包）数据集的陷阱形状与旧案例**不同**，且 L1/L2 都盖不住：

| | 旧（XM，已退役） | 新（恒锐动力，实测） |
|---|---|---|
| 少发的部分怎么解释 | 有一张自建单据记「已审批损耗」 | **没有任何解释文档**——订单被人工置为 `Closed` |
| 漏看的形态 | 没打开那张下游单 | 那张单不存在，字段就在订单上 |
| 真正的坑 | 少看一层血缘 | **一整批产出从订单侧不可见** |

成品仓积压 1,010 台 = 入库 2,000（自制工单 1,000 + 外协收货 1,000）− 发货 990。
外协那 1,000 台在 ERPNext v15 的结构上**挂不回销售订单**（`Subcontracting Order`
没有 `sales_order` 字段），沿订单查得再深也看不见它——**必须从库存流水反查凭证**。

```
规则 L3：作答涉及某个仓库的库存数量 → 必须已对该库存的全部入库来源逐个 doc.get，且来源集合覆盖库存流水里每一张使数量增加的凭证
违反：拒绝该 answer，回注强制续跑消息
```

→ **L1/L2 管「顺着链条查得够不够深」，L3 管「入库来源查得够不够全」**：
前两条是**深度**，第三条是**覆盖**。

⚠️ **L3 的措辞必须保持通用**，不得出现任何具体单号、DocType 名或数量。它是照着一个
已知陷阱设计的，天然对那个陷阱有效；写进具体单号就成了「照答案写规则」，实验会自证为真
而毫无信息量。判据 `tests/unit/test_evidence_gate_l3.py` 用一条与该陷阱无关的合成轨迹反测。

三条的可执行形式是 `agenerp/tools_readonly.py` 的 `EVIDENCE_GATE`，挂在**作答类工具**
`ANSWERING_TOOLS = ("query.read", "snapshot.read")` 的前置条件上——它们的返回值就是答案里
的数字。`doc.get` / `doc.links` 本身是 L1/L2 要求的取证步骤，**不挂**门禁（挂了就成循环依赖：
L1 会卡住第一次 `doc.links`）。

→ 这是 §7 工具契约的一个特例：**只读工具也有契约，其前置条件约束的是「什么时候允许停下来」。**

#### ② 洞察 Agent：自由巡检发现不了跨单据的业务荒谬

Spike 08 实测：给老板身份、34 个业务 DocType 只读权限、开放式指令「你自己找异常」，
Agent 找到了两笔逾期账款（应收 ¥18,612、应付 ¥2,200），**漏掉了 1,010 台积压**，
并明确把该区域判为「✅ 正常」（依据：`achievement_rate = 100%`）。

原因是两类异常的可发现性根本不同：

| | 逾期账款 | 积压 1,010 台 |
|---|---|---|
| 异常在哪 | **一个字段上**（`status = "Overdue"`） | **不在任何字段上** |
| 发现方式 | 列出发票看状态 | 汇总入库 − 出库，对照订单量判断「多出来的有没有道理」 |
| 前提 | 会查即可 | **必须先知道「产出远大于销出」是个问题** |

> ⚠️ 单位口径同 ①：Spike 08 跑在退役前的 XM 数据集上，数量骨架原样保留，「米」已改「台」。

→ **「无需指令」成立，「无需规则」不成立。** 洞察 Agent 必须由行业包的业务合理性规则驱动，
自由发挥只能找到字段级异常。这给了行业包一个不可替代的存在理由，见 §8.6 结论三。

### 5.1 各 Agent 的工具集

| Agent | 工具 |
|---|---|
| 解释 | `query.read`（精确查询）、`schema.search`、`snapshot.read`、`lineage.trace`（单据血缘）、`rule.lookup`（行业规则）、**`system.overview`**、**`permission.scope`** |
| 洞察 | 解释的全部 + `anomaly.scan`（按行业包规则巡检）、`benchmark.compare` |
| 视图 | `dsl.schema`、`field.catalog`、`dsl.validate`、`dsl.preview`、`bundle.write`（写定制包） |
| 操作 | `doc.create` / `doc.update` / `doc.submit`（**全部受 `before_submit` 门禁约束**）、`workflow.action`、解释的全部只读工具 |
| 形态 | `meta.custom_field`、`meta.doctype`、`meta.property_setter`、`meta.permission`、`bundle.write`、`bundle.diff`、`migration.plan` |
| 编排 | `agent.dispatch`、`task.decompose` |

> ⚠️ **P2.3 落地时对「视图」这一行有一处偏离，人 2026-08-28 当场裁定**（表体不改，注解在此）：
>
> **`dsl.validate` / `dsl.preview` 没有做成模型可见的工具**，而是由视图 Agent 的控制循环
> **无条件执行**（`agenerp/views/loop.py`）。理由是 D-15「规则能覆盖的流程不 Agent 化」——
> 「这个视图合不合法」「哪一块画不了、为什么」`validate()` 与 `plan_render()`
> 纯规则零模型就能答；做成工具，模型就有了「不调它就交」这条路。
> 同形先例：`permission.scope` 也不进模型工具面（由开场注入确定性化）。
>
> **能力没有少**：视图交付走一个 `view.submit` 工具，参数是由 DSL 封闭取值生成的 JSON Schema，
> 交完由循环跑完整两层校验 + 落回判定。判据 `tests/agents/test_view_agent.py`
> 里有一条专门断言这两个名字**不在**工具面上。
>
> `dsl.schema` / `field.catalog` 未做：视图 Agent 用 `schema.search` + `meta.fields`
> 达成同一件事（P2.0R 实测的主力就是这两个），**没有第三份 schema 入口**。
> `bundle.write` 属 P2.4。**本注解可逆** —— 要改回字面，加两份契约 + 注册表项即可。

**设计要点**：工具不是裸 CRUD。每个工具是一份**契约**（见 §7），声明前置条件、后置断言、风险等级、所需权限。

**`system.overview` 与 `permission.scope` 由 Spike 01 实测产出**（见 `spike/FINDINGS.md`）：

- `system.overview` —— 冷启动时一次给出公司、核心 DocType、数据时间范围。实测中缺它导致模型把公司名当客户名查，白费 2–3 次调用。
- `permission.scope` —— 开局即告知当前身份的可见范围。实测中缺它导致权限不足的用户提问时工具调用量放大约 5 倍（7 → 35 次），见 §7.4。

> **Spike 02 复测：补上 `permission.scope` 后，同一道越权问题的工具调用从 35 次降到 1 次。**
> 这不是优化，是量级变化。因此该工具**由控制循环在会话开场自动注入，不依赖模型想起来调用**。
>
> 两条实现约束（都是踩出来的）：
> 1. **必须逐个调 `frappe.has_permission`，不能从 DocPerm / Custom DocPerm 表反推。**
>    反推的版本漏报了 `Sales Invoice`——而该用户明明读得到。**漏报比噪声更危险**：
>    Agent 会据此错误地拒绝回答。
> 2. **必须按 app 过滤掉 Frappe 框架自身的 DocType。** 不过滤时老板 83 个、工人 61 个，
>    其中九成是 Token Cache / Desktop Icon / Voice Call Settings 这类管道，纯 token 噪声；
>    过滤后分别是 34 个和 12 个。
>    → **工具契约必须包含 `returns` 的裁剪规则，不能把后端能查到的东西原样倒给模型。**

**洞察那一行在本仓的落点（P1.5 · 2026-08-24 · 只补指针，§5.0 ② 的实测结论一个字未动）**：
D-15 把「洞察」拆成了两件东西 —— **巡检（按清单逐条查、命中即报）是代码**，
落在 `agenerp/inspection/`（纯规则引擎，零 LLM）；**归因（为什么会这样、要不要紧）才是模型**，
落在 `agenerp/insight/`，取证走 P1.4 的解释循环（`agenerp.explain.explain`）与证据充分性门禁。
边界与四个 `Decision` 见 `docs/architecture/module-boundaries.md` **§7.9**。
⚠️ 上表洞察行里的 **`anomaly.scan` 与 `benchmark.compare` 仍未实现**：
它们不在十个只读契约里（`agenerp/tools_readonly.py` 逐字给了排除理由「依赖行业包规则」），
P1.5 也没有新增契约。⚠️ `agenerp/inspection/` 自带的最小规则集**不是行业包制品** ——
行业包 v0 由 **P1.6 交付**（`industry-packs/discrete/pack.json`，三条规则各带 `test_case`，
校验器与 CLI 在 `agenerp/packs/`，落点节 `docs/architecture/module-boundaries.md` **§7.10**）。
⚠️ **`rule.lookup` 仍然指名报错**，但理由变了：不再是「本仓没有行业包」，
而是「**包在盘上、尚未接线**」—— 接线会让 `tests/gates/test_tool_execution_live.py` 的一条由绿转红，
复绿只能改裁判或改它委派的断言体，两者都在红线内，**接线由人裁定**（见 `docs/masterplan/STATE.md` §3）。
⚠️ **归因那一半的首次活端点实跑（2026-08-25）落点节是 `docs/architecture/module-boundaries.md` §7.16**
（本行**只补指针**，§5.0 ② 与上面这段的结论一个字未动）：它证明的是这条链在真站点上走得通、
零越权零写、账目对得上；**它没有产出任何归因文本**（`accepted = false`），
原因是一个已登记的活缺陷 `docs/bugs/03-doc-links-dies-on-single-doctypes.md`。

**`lineage.trace` 的硬约束**：ERPNext 的单据关联大量挂在**子表**上（如 `Delivery Note Item.against_sales_order`）。只扫主表 Link 字段的血缘实现会返回空结果——实测中 21 个指向 Sales Order 的 Link 字段里，14 个在子表。血缘工具必须同时扫主表级与子表级并回溯父单据。

## 6. 角色 × Agent 矩阵

以 XM 的七类角色为样例（实际由行业包定义）：

| 角色 | 解释 | 洞察 | 视图 | 操作 | 形态 | 默认首页 |
|---|---|---|---|---|---|---|
| 老板 | ✅ 全域 | ✅ 全域 | ✅ 自己的视图 | ❌ | ❌ | 经营结论页 |
| 财务 | ✅ 财务域 | ✅ 财务域 | ✅ | ✅ 发票/凭证 | ❌ | 待开票 / 应收 |
| 业务员 | ✅ 销售域 | ✅ 销售域 | ✅ | ✅ 报价/订单 | ❌ | 我的报价与订单 |
| 生产计划员 | ✅ 生产域 | ✅ 生产域 | ✅ | ✅ 工单/BOM | ❌ | 排产看板 |
| 车间工人 | ⚠️ 仅本工序 | ❌ | ❌ | ✅ 报工/异常 | ❌ | 我的任务卡 |
| 质检员 | ✅ 质量域 | ✅ 质量域 | ✅ | ✅ 质检单 | ❌ | 待检列表 |
| 仓库/外协 | ✅ 库存域 | ✅ 库存域 | ✅ | ✅ 收发货 | ❌ | 待收发 |
| 实施顾问 | ✅ | ✅ | ✅ | ✅ | ✅ | Desk |

**硬约束**：矩阵中的「域」不是 Agent 自己判断的，而是**由 Frappe 的 Role/DocPerm/User Permission 后端强制**。Agent 拿到的查询结果本身就已经过滤过。Agent 无权、也无法扩大自己的可见范围。

**已知陷阱（Spike 09 精确实测，比原记录更严重）**：Frappe 的权限**实为五层且几乎不联动**。

| 层 | 载体 | 老板实测 | 工人实测 |
|---|---|---|---|
| ① DocType | `DocPerm` / `Custom DocPerm` / `User Permission` | 可读 83 / 466（业务 34） | 可读 61 / 466（业务 12） |
| ② Report | **`Report.Has Role`（主导）** + ref_doctype 读权限 | 可开 **10 / 196** | 可开 **1 / 196** |
| ③ Workspace 可见性 | `Workspace.Has Role` | 可见 20 / 20 | 可见 19 / 20 |
| ④ Workspace 内容 | 每条链接按目标类型独立判定，渲染时过滤 | 渲染 62 / 409 声明链接 | 渲染 18 / 397 |
| ⑤ 渲染 API 访问检查 | `get_desktop_page` 自带，独立于 ③ | 5 个工作台被拒 | 11 个被拒 |

三条比原记录更要命的发现：

1. **报表打不开，98.9% 与 DocType 权限无关。** 老板打不开的 186 张报表里，184 张是被**报表自身的 `Has Role` 子表**挡住，只有 2 张是 ref_doctype 权限问题。
   → 给老板加 DocType 只读权限，对报表可见性**几乎毫无作用**。`meta.permission` 必须写 `Report.Has Role`。
2. **③ 几乎不挡人，于是 ④ 制造了空壳。** 用户看到的不是「点不开的链接」（Frappe 会过滤掉），而是**一排几乎全空的房间**：老板 8 个、工人 13 个工作台完全空壳，其中包括 **`Home`——默认首页，对两个角色都渲染出 0 个链接**。这就是附录 A #4「入口零引导」的机制性解释。
3. **全站唯一 100% 可用的工作台是手工搭的 `XM 花型智造`（12/12）。** 从反面印证 §4 与 §10：能用的界面必须按角色重新组织，不能把原生工作台开放给用户。

**实现陷阱**：`frappe.has_permission` 对部分 Single DocType（如 `System Health Report`）**抛异常而非返回 False**（其控制器在 `load_from_db` 中调 `frappe.only_for`）。任何遍历权限的工具都必须 try/except 兜住。

→ **`meta.permission` 的后置断言不能以「写了几条 DocPerm」为判据，必须以「用户能看到什么」为判据**：

```yaml
postconditions:
  - 目标角色对 X 的 DocType 读权限成立
  - 与 X 相关的 Report 的 Has Role 已含该角色
  - 该角色首页渲染出的链接数 > 0     # 直接调 get_desktop_page 断言，可进 CI
```

## 9. 风险分级与审批

> **命名消歧**：本节的 L0–L3 是**风险档**（决定要不要人批）。
> §5.0 ① 的 L1–L3 是**证据门禁**（决定什么时候允许停下来）。两套编号同名不同义，
> 下表以及全文引用本表时一律读作**风险档 L0 / L1 / L2 / L3**。

| 档 | 定义 | 例子 | 执行路径 |
|---|---|---|---|
| **L0** | 只读，无副作用 | 查询、解释、生成视图 DSL 草稿 | 直接放行 |
| **L1** | 可逆配置 | 应用视图 DSL、Workspace 调整、Custom Field 增加 | 提示后放行，落定制包 |
| **L2** | 业务数据写入 | 建单、提交、报工、审批 | 走 `before_submit` 门禁；金额/数量超阈值需人批 |
| **L3** | 系统形态变更 | 新建 DocType（DDL）、改权限、改 Workflow | **强制人批** + 落 git + 可回滚 |

**风险档 L3 中的 Server Script 特别处置**：Server Script 是任意 Python，运行时注入等同 RCE。
→ **Agent 永不允许生成运行时 Server Script。** 需要服务端逻辑时，生成代码 → 落 git → 人工 review → 走 app 部署流程。

**审批 gate 必须长在 Agent 控制循环里**，不能是外挂检查——这是采用任何第三方 harness 时必须替换其 agent loop 插件的原因。
