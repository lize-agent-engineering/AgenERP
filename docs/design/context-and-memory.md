## 8. 上下文、知识与记忆架构

### 8.1 四类知识的边界

| 知识 | 例子 | 住哪 | 技术 |
|---|---|---|---|
| ① 结构化事实 | 库存、金额、单据 | 已在 DocType | **精确查询，绝不用 RAG** |
| ② Schema 元知识 | 有哪些字段、什么含义 | 数据库，量大 | 向量索引**元数据** |
| ③ 行业知识 | 什么是合理损耗 | 行业包 + **DocType 建模本身** | **结构化规则** + 少量文档 RAG，见 §8.6 |
| ④ 公司特有知识 | 客户 A 不接受 2% 以上损耗 | Memory | **DocType** |

**为什么 ERP 事实绝不进向量库：**
1. 数字问题必须精确，相似度检索无意义
2. ERP 数据实时变化，索引永远滞后
3. 向量库没有 RBAC，embedding 之后权限边界消失 —— **这是数据泄露，不是不方便**

→ Agent 用 **text-to-query**，不用 RAG。

**② 的实现方式已被 Spike 07 修正：结构化导航优先，向量检索降级为兜底召回。**

原设计假定 schema 元知识靠向量索引。在本站点 9,776 个有效字段上实测（`qwen3-embedding:0.6b`，20 个真实中文业务问句）：

| 索引范围 | 字段数 | 索引文本 | Top-1 | **Top-5** | Top-10 |
|---|---|---|---|---|---|
| 业务 app 全量（542 DocType） | 7,340 | schema 字面 | 30% | **55%** | 60% |
| 业务 app 全量 | 7,340 | 人话描述 | 55% | **60%** | 75% |
| 仅有数据的 DocType（88 个） | 2,516 | schema 字面 | 40% | **60%** | 75% |
| **仅有数据的 DocType** | **2,516** | **人话描述** | **65%** | **75%** | **90%** |

**最好一档 Top-5 = 75%，未达可用线。** 失败方式高度统一——**语义对了，单据错了**：
「发票还有多少没收回来」返回 `Purchase Invoice` 的字段，「总账借方金额」返回
`Journal Entry.total_debit`。ERPNext 里 `qty` / `warehouse` / `debit` 在几十个
DocType 上重复出现，字段级 embedding 天然分不开「哪一张单」。

先检索 DocType 再列字段的两段式**更差**（DocType 级 Top-5 仅 50%），因为
`Sales Order` / `Production Plan Sales Order` / `Sample Order` / `Blanket Order`
这些名字本身就高度混淆。

#### 🔴 2026-08-26 · P2.0R 在**本仓、本站点**复测，把瓶颈钉在了「选单据」这一层

Spike 07 是在 XM 证据仓里做的。按 D-16，那个 75% 不能当本仓基线。本仓自己的数
（站点 `frontend`，465 个业务 DocType / 6,350 字段，**同一个 `qwen3-embedding:0.6b`**）：

| 索引范围 | 索引文本 | Top-1 | **Top-5** | Top-10 |
|---|---|---|---|---|
| 现役 `schema_search`（DocType 名+模块名子串匹配） | — | **0%** | **0%** | **0%** |
| business 6,350 字段 | 人话描述 | 30.0% | **65.0%** | 70.0% |
| live 2,042 字段 | 人话描述 | 40.0% | **62.5%** | 70.0% |
| 🔴 **oracle：把 ground-truth DocType 直接给定** | 人话描述 | **70.0%** | **97.5%** | **100%** |

**把 DocType 固定住，Top-5 从 62.5% 跳到 97.5%，Top-10 = 100%。40 条只错 1 条，
而那一条错在同一张单据内部**（`Delivery Note Item.qty` 被 `actual_qty` / `packed_qty` 压住）。

⇒ **瓶颈在「选哪一张单」，不在「选哪个字段」。**
⇒ **换更大的嵌入模型不是解法** —— 与 D-22.4 同源：问题不是语义表示不够好，
是系统不知道用户说的是哪一张单。主攻方向定为 **DocType 消歧（结构化召回）**。

⚠️ **97.5% 是 oracle 上界，不是可交付的检索器**，不得据此宣称 P2.0R 已达标。

##### ⛔ 第二轮（同日）：**第一个试的机制被实测推翻了**

顺着「主攻 DocType 消歧」做的第一件事是**按单据族（父表 + 它挂的全部子表）做两段式收敛**：
先把字段分数聚合到族、取 Top-3 族、再在其字段内排。

| | recall@1 | recall@3 | **recall@5** | recall@10 |
|---|---|---|---|---|
| DocType 级（字段分数 max 聚合） | 37.5% | 67.5% | **77.5%** | 85.0% |
| DocType 级（单独建描述向量） | 20.0% | 40.0% | **42.5%** | 65.0% |
| **单据族**（字段分数 max 聚合） | 45.0% | 70.0% | **82.5%** | 85.0% |
| **两段式合成 → 字段 Top-5** | — | — | **60.0%** | — |

**60.0% 比什么都不做的 65.0% 还低。** 机制查明：两段式的天花板就是第一段的
族 recall@**3** = 70.0%，剩下 30% 在第二段开始前就被硬切掉了；
而硬切换来的「收敛」只是把候选从 6,350 降到中位 310 个字段。
⇒ **不可逆的召回损失 > 候选集变小的收益。**

> 这与 Spike 07「两段式检索更差，不是解法」是同一结论，**但用一个信息量大得多的信号
> 重新撞出来**（族 recall@5 = 82.5%，远好过 Spike 07 的 DocType Top-5 = 50%）。
> **信号变好了，两段式照样输 —— 输的是「硬切」这个动作本身。**

**另一条顺带证实的**：DocType 级独立描述向量（42.5%）比拿字段分数聚合上去（77.5%）
**差 35 个点** ⇒ **DocType 的可检索信息主要在它的字段里，不在名字和模块里。**

⇒ 按判定表：**该机制不进实现**；**并且不许接着挑下一个机制**，须回到判定表重新设计
（D-16）。详见 plan [`2026-08-26-P2.0R-2-…`](../plans/p2-views/2026-08-26-P2.0R-2-doctype-disambiguation.md)。

⚠️ **`live`（只索引有数据的 DocType）过滤器在本站点是净亏的**（65.0% → 62.5%），
与 Spike 07 上的 +15 点相反。逐题拆开机制干净：**新中 4 条、丢掉 5 条**，
而丢掉的 5 条**恰好是答案 DocType 行数为 0 的那 5 条**。
⇒ 该过滤器的净收益 = 干扰项减少的增益 − 正确答案被误杀的损失，
**由站点数据宽度决定，不能无条件启用**。

证据与原样复跑：[`tools/experiments/p2_schema_retrieval/`](../../tools/experiments/p2_schema_retrieval/README.md) ·
plan [`2026-08-26-P2.0R-…`](../plans/p2-views/2026-08-26-P2.0R-schema-retrieval-bottleneck-localization.md)（预测 `e82f73d` 早于结果，git 时间戳可查）。

**而 Spike 02 的受约束 Agent 四道探针全部通过，全程没有用到任何向量检索。**
它用的是 `system.overview` → `meta.fields` → `doc.links`。**结构化导航打赢了语义检索**——
ERP 的 schema 是强结构的，把它压平成向量再用相似度找回来是自找的信息损失。

→ 修正后的 ②：

> ② schema 元知识 → **优先结构化导航**（`system.overview` / `meta.fields` / `doc.links`）；
> 向量检索仅作**兜底召回**，且必须按「召回器」而非「选择器」设计——
> Top-10 有 90% 而 Top-1 只有 65%，检索只负责给候选清单，由模型结合 `meta.fields` 定夺。

两个各值约 15 个点的杠杆（若要做）：**只索引表里真有数据的 DocType**（本站点 542 → 88，
干扰项几乎全部来自空表），以及**索引人话描述而非 schema 字面**。

另有一条文档此前未提及的条件：**用户用中文问，ERPNext 的 schema 是英文的**，这是跨语言检索。
→ §10 的术语层因此不只服务呈现，**也是检索质量的前置条件**。

### 8.2 上下文四层

| 层 | 内容 | 生命周期 | 实现 | 可替换 |
|---|---|---|---|---|
| ① 即时 | 当前单据、角色、视图 | 一次请求 | 前端注入 · **本仓落点** `agenerp/context/immediate.py`（`assemble` / `trim`，见 `module-boundaries.md` §7.7）· **循环侧接入点** `agenerp/explain/loop.py`（`explain(immediate=...)` → 一条独立的 `system` 消息，见 `module-boundaries.md` §7.12） | — |
| ② 会话 | 对话历史、已执行动作、前后快照 | 一次会话 | Session → DocType · **本仓落点** `agenerp/context/session.py` + `store.py`（端口 + 零依赖内置实现）；DocType **声明**在 `agenerp/context/doctype/`，**活站点上尚未建表**（风险档 L3 强制人批） | ✅ |
| ③ 记忆 | 组织 / 角色 / 个人知识 | 长期，会过时 | Memory DocType | ✅ |
| ④ 检索 | schema 元知识、行业文档 | 静态/半静态 | 检索工具 | ✅ |

**上下文窗口工程**不是其中一层，是横切四层的策略。ERP 特有的优先级规则：

1. 当前单据的完整字段永远优先，① 不可裁剪
2. 已执行动作的审计记录不可压缩（要追责）
3. 记忆按「是否已验证」排序，未验证的先裁
4. schema 按检索相关度裁

### 8.3 Memory as DocType

公司特有知识不能是外挂向量库——那是黑盒，看不见、改不了、无法溯源。落成 DocType 后自动获得：列表界面（**用户能看到系统记住了什么**）、编辑删除、权限控制、版本历史、审批流、Link 到证据单据。

**三层粒度**：

```
组织记忆   公司级规则、惯例、客户偏好      全员共享，改动需审批
角色记忆   岗位操作习惯                   角色内共享
个人记忆   个人操作偏好                   个人可见
```

### 8.4 记忆分级与安全红线

Memory 是**持久化的 prompt injection 入口**。有人在评论里写「忽略之前的规则」被存成记忆，从此每次生效。

| 类型 | 可否验证 | 处理 |
|---|---|---|
| 事实型 | 可查数据库核对 | 验证后存，标记已验证 |
| 偏好型 | 不可 | 存，标记来源与时间，**不参与风险决策** |

**硬红线（代码级，不可配置）：**

> **Memory 永远不能影响权限判定和风险等级。**
> 权限只来自 Role/DocPerm；风险等级只来自工具契约。任何记忆都不能提升 Agent 权限或降低动作风险档位。

### 8.5 可替换实现与 adapter 边界

```
        我们的 Context & Memory 抽象层（内核，接口固定）
                        │
        ┌───────────────┼───────────────┬──────────────┐
        ▼               ▼               ▼              ▼
   内置实现        MyContext        Harness        社区
  (DocType,       adapter          session       adapter
   零依赖)       (蒸馏引擎)
```

**内置实现必须存在且零外部依赖。** MyContext（千问办公开源，本地运行、全程可溯源、冲突交用户确认）是增强插件，不是前提。其设计原则与本文 §8.3–8.4 高度一致，可作为参考实现；但其数据源（钉钉/飞书）与粒度（个人档案）需适配。


### 8.6 行业包：结构良好的 DocType 就是行业知识

**这一节由 Spike 01 实测推翻了原设计。**

原假设：Agent 要理解「合理损耗」这类行业概念，必须由行业包显式提供规则定义。

实测结果：**未向模型提供任何行业规则**，冷启动的模型仍正确推出了合理损耗的业务含义、并给出了比预设答案更准确的根因诊断。原因是 `Loss Review` 这个 DocType 的字段名本身已经编码了语义：

```
approved_loss_quantity      获批损耗
expected_delivery_quantity  理应发货
achievement_rate            达成率
```

字段名 + 字段间的数值关系 + Link 到 Work Order 的血缘，三者合起来已经把业务概念表达完整了。

#### 结论一：行业包不重复 schema 已有的语义

行业包只负责 **schema 装不下的东西**：

| 属于行业包 | 不属于行业包 |
|---|---|
| 阈值（达成率 <98% 红 / 98–100% 绿 / >100% 蓝） | 「什么是获批损耗」——字段名已表达 |
| 预警规则（成品无对应订单且 >N 天 → 异常） | 「损耗复盘关联哪张工单」——血缘已表达 |
| 跨单据业务约束 | 「达成率怎么算」——字段关系已表达 |
| 术语映射修正（`In Process` → 过程检验） | |
| 说不清的工艺经验（走文档 RAG） | |

这比原设计窄得多，也因此可行得多——行业包的编写成本从「把行业知识写一遍」降到「补充 schema 表达不了的判断标准」。

#### 结论二：DocType 建模质量直接决定 Agent 能力

这是更强、也更有行动含义的推论：

> **把行业知识建模进 DocType，本身就是在给 Agent 喂知识。**

一个字段名叫 `qty2` 的系统，Agent 无从理解；一个字段名叫 `approved_loss_quantity` 并 Link 到工单的系统，Agent 不需要额外说明就能推理。

因此：

- **行业包设计原则**：优先通过 DocType 建模表达知识，其次才用规则声明
- **形态 Agent 的评价标准**（§5）不只是「生成的字段能用」，还包括**「生成的字段名与结构是否让后续 Agent 更容易理解」**
- 这也为「保留复杂度，隐藏复杂度」（§1.4.3）提供了第二个理由：**结构完整的 ERP 内核不只是业务正确性的保障，也是 Agent 智能的来源**
