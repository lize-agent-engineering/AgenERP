## 附录 A：实测发现的问题清单

在真实 ERPNext v16 + ERPNext 16.32.1 + Frappe 16.31.0 实例上（老板角色登录）实测得出，每一条都是需求来源：

| # | 问题 | 证据 | 归属章节 |
|---|---|---|---|
| 1 | 术语机翻事故 | `Masters`→「大师」；`In Process`→「进行中」（**语义翻反**，实为过程检验）；会计科目全英文；自定义 DocType 字段零翻译 | §10 视图 DSL 的 label 生成 |
| 2 | 状态与业务现实错位 | 销售订单卡在「待出货」，实际 990 米已发、10 米为已审批合理损耗 | §5 解释 Agent |
| 3 | 数字无基准 | 毛利率 61.32% 无任何参照 | §10.2 `metric` 块 |
| 4 | 入口零引导 | 启动页 10 个图标无说明；老板工作台 12 个链接、0 个数字 | §4 三端模型 |
| 5 | 权限意图难落地 | 老板对 21 个 DocType 只读，却只能打开 196 张报表中的 11 张 | §6 权限分层陷阱 |
| 6 | 定制冗余 | Job Card 上原生与自定义质检字段并存且同值 | §11.3 |
| 7 | 门禁全过但业务荒谬 | 造 2,000 米、卖 990 米、积压 1,010 米 | §13.2 |
| 8 | 异常单挂起而下游已放行 | `ISSUE-00002` 仍为 Investigating/草稿，工单、发货、开票却均已完成。**属字段级异常**（`status`/`docstatus` 上直接可见），与 #7 的跨单据荒谬不同类，可发现性远高 | §13.2 |
| 9 | 用户可写字段构成注入面 | `Production Issue.resolution` 工人可写、老板只读，形成提权路径 | §7.5 |

| 11 | `sync_customizations` 是纯 upsert，revert 无效 | 从定制包删掉字段再 sync，站点上字段纹丝不动 | §11.1 |
| 12 | 定制包导出物含易变字段 | 含 `modified`/`creation`/`owner`/`_comments`，不改也产生 diff | §11.1 |

| 14 | schema 向量检索在真实规模下不可用 | 9,776 字段、20 个中文问句，最好 Top-5 仅 75%；失败方式统一为「语义对、单据错」 | §8.1 |
| 15 | 洞察 Agent 自由巡检漏掉 #7 | 找到两笔逾期账款，漏掉 1,010 米积压，并判该区域「正常」 | §13.2、§5.0 ② |

### B.1 未排除的残余风险（必须显式承认）

| 风险 | 为什么没排除 | 建议何时排除 |
|---|---|---|
| **写权限下的注入** | Spike 04 的 Agent 是 L0 只读。操作 Agent 拿到写工具后，同样载荷的后果完全不同 | **P3 之前必须重测** |
| **Memory 投毒**（§8.4） | 本轮无记忆层 | 随 Memory v0 |
| **跨站点迁移** | Spike 06 未建第二站点，「可迁移」是从 upsert 幂等性**推断**的 | P2 |
| **重估值链路的事务外副作用** | Spike 05 的倒填日期未真正触发 `Repost Item Valuation` | P3 |
| **U8 的解法** | 只做了现状测量，`meta.permission` 尚未实现 | P4 |
| **统计显著性** | 所有 Agent 探针每题各跑 1 次，无重复实验 | P5 评测集 |
| **门禁规则的过拟合** | 证据充分性门禁是从失败样本反推的，通用性未在新题目上验证 | P1 |
| **零依赖栈未真正启动** | 只验证到 `docker compose config` 解析通过 | P0 |
| **模型可能已在预训练中见过 ERPNext** | 无法排除；对所有基于开源 ERP 的 Agent 项目同样成立 | 系统性因素，不可排除 |
