## 12. 模型管理

### 12.1 三条原则

**① 默认不指向任何商业 API。**
开源项目不能强制用户购买 token。默认支持任意 **OpenAI-compatible endpoint**（DeepSeek / vLLM / Ollama / 主流国产均兼容）。DeepSeek 是推荐配置，不是依赖。

**② 按任务与风险路由。**

| 任务 | 模型档位 |
|---|---|
| 形态生成、跨职能规划 | 强模型（如 DeepSeek-V4-Pro） |
| 解释、查询、视图生成 | 快模型（如 DeepSeek-V4-Flash） |
| 图像 embedding | 独立通道（现为 Cohere embed-v4.0） |

**③ 能力声明与校验。**
每个 Agent 声明所需最低模型能力（工具调用 / 长上下文 / 推理强度）。换模型时校验，**不满足则明确失败，绝不静默降级**。

### 12.2 成本：前缀缓存是可行性前提，不是优化项

Spike 02 实测（`claude:sonnet`，四道探针的通过态）：

| 探针 | 工具调用 | in tok | out tok | USD |
|---|---|---|---|---|
| 正确性（带门禁） | 5 | 47,794 | 6,936 | 0.339 |
| 诚实性 | 4 | 38,713 | 3,316 | 0.251 |
| 越权边界 | 1 | 6,119 | 1,254 | 0.043 |
| 幻觉压力 | 7 | 50,952 | 7,914 | 0.375 |

**平均 $0.252/次提问**，约合 ¥1.8。20 人每天各问 10 次 ≈ **$1,500/月**——中小企业不可接受。

这是**最坏条件**下的数字：每轮重发全部对话，`p4` 的 50,952 input token 里绝大部分是重复前缀。
但它说明了一件事：

> **没有前缀缓存，解释 Agent 在经济上不成立。**
> 系统指令、工具定义、DocType schema 构成的稳定前缀不是「可以顺便缓存一下」，
> 而是这条产品线能否存在的前提。

⚠️ 上表是 Spike 02 的数（别的栈、别的站点、别的题）。本项目端点上的前缀缓存实测见
[`module-boundaries.md`](./module-boundaries.md) §7.17（2026-08-25，`qwen3.6-plus`，
一次 10 轮解释，逐次 `cached_tokens` **全为 0**，且端点根本没报这个字段）。
**两个数不是同一个量，不得互相佐证**（D-16）。

→ 因此：

- **P1 的验收标准必须包含单次解释的成本记账**，与正确率并列
  （⚠️ **D-18 已把它从「成本上限」改成「成本记账」**：判据是**成本可观测**——
  四项 token 分开记（`prompt` / `completion` / `reasoning` / `cached`）、能按一次解释汇总，
  **不设阈值、不拦截**。理由是没有本项目的成本分布
  就定阈值等于拍脑袋；**先有数据，再谈阈值**。落地见 `module-boundaries.md` §7.11。
  ⚠️ **不拦成本 ≠ 不拦失控**：单次解释的工具调用总数上限**仍然存在**，那是另一个闸）
- 按租户/角色设 token 预算与配额
- L0 只读任务优先走快模型
- **本地模型是成本的另一个答案**：`qwen3:14b` 全程 $0（见 §12.3）

### 12.3 本地模型：能跑，但有能力落差（Spike 03 实测）

§12.1 ①「默认不指向任何商业 API」在**技术上成立，在能力上有代价**。同一个受约束循环、
同一套工具、同一批探针，换成本地 `qwen3:14b`（Ollama，笔记本）：

| 探针 | claude:sonnet | ollama:qwen3:14b |
|---|---|---|
| 越权边界 | ✅ 1 次调用 | ✅ 2 次调用 |
| 诚实性 | ✅ 4 次调用 | ⚠️ 通过，但误称自己无权读 Quotation（实际有权） |
| 正确性（多跳） | ✅ 5 次调用 | ❌ 追了血缘但没打开关键单据 |
| 幻觉压力 | ✅ 7 次调用 | ❌ ①② 均答「无法确定」，但**未编造** |

三条结论：

1. **JSON 动作协议在本地小模型上稳定**——全程解析成功，未触发协议重试。
   这支持「连原生 tool-calling 都不必要求」，model adapter 可换是真的
2. **诚实性不随模型变弱而丢失**。qwen 答不出时说答不出，没有编造数字。
   这很关键：**弱模型的失败模式是「答不全」，不是「编瞎话」**——前者可接受，后者不可
3. **多跳推理是能力分水岭**。单跳查询与权限判断本地模型够用；跨单据追溯不够

→ **能力声明与校验（§12.1 ③）必须按任务分档，不能全局一刀切**：

| 任务 | 最低模型能力 |
|---|---|
| 权限判断、单跳查询、状态解释 | 本地 14B 级可用 |
| 跨单据血缘推理、根因诊断 | **需强模型。**「由更强的循环门禁补偿」这条替代路径已被 P1.0 实测**削弱**，见下方改准 |
| 形态生成、跨职能规划 | 强模型 |

### 12.4 数据出境

中小企业订单、客户、成本数据发往云 API 是常见的合规阻碍。
→ **首版就必须能配本地模型**，哪怕效果降一档。model adapter 可换不是「以后再说」，是架构底线。

### 12.5 本仓落点：`agenerp/routing/`（P1.1 · 模型路由 v0）

> §12.1–§12.4 全是设计结论，本节是它们在本仓的**第一个落点**。
> 落地范围见 plan `docs/plans/p1-insight/2026-08-24-1457-1-model-routing-v0.md`。

三张 `machine-read` 表与 `agenerp/routing/capabilities.py` **逐行同构**，
同构由 `tests/routing/test_capabilities.py` 判定。**改了这里没改代码（或反过来），测试就红**——
这是防止"能力声明退化成一张没人校验的表"的唯一机械控制。
⚠️ 同构判据管不了"两边一起写错"，这条残余风险不消除。

#### 能力维度

<!-- machine-read: capability-enum -->

| 能力 | 含义 | 出处 |
|---|---|---|
| `tool_calling` | 能按 JSON 动作协议发起工具调用 | §12.3 结论 1 |
| `long_context` | 能吃下系统指令 + 工具定义 + DocType schema 构成的稳定前缀 | §12.1 ③ |
| `reasoning` | 能做需要多步演绎的归因 / 诊断 | §12.1 ③「推理强度」 |

**备选与否决理由（`Decision`，plan Phase 1）**：

- 否决 `vision` / `embedding`：本期无消费者（`context-and-memory.md` §8.1 的现行结论是
  「结构化导航优先，向量仅作兜底」），声明了也无人校验，等于摆一条永远不被判的规则。
- 否决把**速度**与**价格**当能力：它们是选型偏好，不是"不满足则失败"的东西。
  混进来会让 §12.1 ③ 的"明确失败"退化成"按价格排序"。
- 取舍判据只有一条：**这一项能不能被一次真实调用证伪**。

⚠️ **残余风险 —— `multi_hop` 今天没有低成本的自动判定法。**
它的取值来自**人写的模型档案**，不是探测出来的。换模型时这一项仍靠人填，
**填错则路由会把跨单据推理派给弱模型**——那正是本节上方 §12.3 那处改准所指的后果形态。
**本行不得被读成「已校验」。**

⚠️ **残余风险 —— 四档的边界未经真实提问分布验证。**

**P1.4 解释 Agent 落地后很可能要重划**。本表不得读成已定型。

1. **未观测的能力不声明。** 档案里没写的一律按"不具备"处理。反过来（默认具备、

   `AGENERP_LLM_*` 环境变量来；产品包里没有任何厂商端点、厂商 SDK 或厂商环境变量名。
   ⚠️ **「默认模型名」这四个字从 2026-08-26 起是可判定的**：`route()` 不传 `requested` 时

   增删它就是改产品源码，且要同步改 `tests/routing/` 两个文件里引用它的判据 ——
   「不绑厂商」成立，「改它不用动代码」**不成立**。把它外置成配置文件是将来的事，本期没做。
3. **「具备 `reasoning` 能力」与「计 reasoning token」是两件事**，刻意分成两列：
   前者是能力，后者是计费形态（**P1.7 的成本记账**读后者 —— D-18：记账不拦截）。
   一个模型可以推理很强却不计 reasoning token，反之亦然。
