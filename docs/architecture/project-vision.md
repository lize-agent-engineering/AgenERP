## 1. 定位与非目标

### 1.1 我们解决什么问题

ERP 的功能不缺，缺的是**可用性**和**适配性**。在真实 ERPNext v16 实例上的实测（见 §附录 A）表明：

- 系统能跑通「报价 → 生产 → 质检 → 外协 → 发货 → 发票 → 总账」全链路，总账借贷分毫不差
- 但业务用户打开后**不知道从哪看起**、**看到的数字没有基准**、**术语是黑话加机翻**
- 而且系统**造了 2000 米、只卖了 990 米**这种业务荒谬，所有自动化门禁全部通过却无人发现

**结论：问题不在功能层，在呈现层、语言层和判断层。而这三层恰好是 LLM 的主场。**

### 1.2 三条设计公理

1. **Agent 能做什么，由业务契约决定，不由 prompt 决定。**
   护栏长在执行路径上，不是写在提示词里。
2. **Agent 的产物必须是可治理的一等公民。**
   配置落 git、记忆落 DocType、动作落审计。没有黑盒副作用。
3. **系统形态由每家企业长出来，但生长必须留痕。**
   LLM 让生成定制的成本趋近于零，这会加速 ERP 定制的死亡螺旋——除非生成的同时就是可 diff、可回滚、可迁移的产物。

### 1.3 明确的非目标

- ❌ 不重写 Frappe Desk（见 §3.2 的证据）
- ❌ 不重造 ERPNext 的会计/制造内核
- ❌ 不做通用 Agent 框架（我们做 ERP 场景的 runtime）
- ❌ 首版不追求覆盖所有行业（内核通用 + 行业包，首个行业包是离散制造）
- ❌ 不承诺替代法定会计与税务申报
- ❌ **不以「降低 ERP 复杂度」为目标** —— 保留复杂度，隐藏复杂度。见 §1.4

### 1.4 与低代码平台的分歧

低代码/零代码平台（简道云、Rebuild 等）与本项目瞄准同一批痛点，极易被误认为同类。分歧必须写清楚。

#### 1.4.1 痛点是共识

低代码厂商的内容营销反复论证 ERP「普遍难用」，归纳的原因通常是五条：系统复杂度高、界面不友好、实施与培训成本高、各家流程独特、定制需求强。

**这五条是真的**——正因为真，这类内容才有流量。**竞争对手替我们论证了痛点存在。**

> 典型样本：简道云《为什么 ERP 系统普遍难用》 <https://www.jiandaoyun.com/blog/article/1840210/>（内容营销，结论导向自家低代码平台；痛点归纳可用，解法结论不采纳）

#### 1.4.2 但解法根本不同

| | 低代码平台 | AgenERP |
|---|---|---|
| 对「复杂度」的处理 | **消除**：换一个简单平台自己搭 | **保留 + 隐藏**：内核不动，用 Agent 隐藏 |
| 代价 | **砍掉业务深度** | 首版界面覆盖窄，未覆盖处落回 Desk |
| 对「定制成本」的判断 | 问题是**定制太贵** → 让它变便宜 | 问题是**定制无法治理** → 让它可 diff / 可回滚 / 可迁移 |
| 定制产物归属 | 锁在平台内，导不出、比不了、迁不走 | **git 中的文本产物** |

#### 1.4.3 为什么「消除复杂度」是错的目标

ERP 的复杂度是**业务本身的复杂度**，不是设计失误。

实测证据：一笔 1000 米订单跑完全链路后，系统自动生成 12 条总账分录，无一条手工录入，借贷各 47,662.00 分毫不差；成本 4,200 材料 + 800 工序 + 2,200 外协全部可追溯到具体单据。**这个能力的代价就是复杂。**

> **任何声称"消除了 ERP 复杂度"的产品，都是砍掉了业务深度。**

低代码平台之所以"简单"，是因为不做 GL、不做 BOM 成本累加、不做库存估值、不做提交后不可变的事务语义。管出入库与审批流足够；算毛利、对总账、追溯成本时露馅。

因此本项目的立场是**保留复杂度，隐藏复杂度**：

- **保留** —— ERPNext 的事务内核一行不动
- **隐藏** —— 角色化窄界面（§4）+ 解释 Agent（§5），使用户无需理解 Stock Ledger Entry 即可掌握经营状况

**若把"降低复杂度"写进目标，本项目将退化为又一个低代码平台——而那条赛道已有多年领先者（见 §2.2）。**

#### 1.4.4 「让定制变便宜」会加速死亡螺旋

Frappe 本已具备低代码能力（Customize Form、Workspace 编辑器、Report Builder）。中小企业未用起来，**不是因为难写，是因为难维护**：定制散落数据库、无版本、无 diff、无法迁移；三年后无人记得某字段的由来；升级即爆炸。

LLM 会把生成定制的成本降到近乎为零。**若不同时解决治理，这只会把死亡螺旋加速一百倍。**

→ 这是 §11 定制包 GitOps 存在的全部理由。

#### 1.4.5 诚实边界

「实施与培训成本高」这一条只能部分解决：

- **培训难 → 大幅改善。** 用户不需要"学会 ERP"，只需要会问（解释 Agent）
- **实施周期 → 部分改善。** 主数据整理、BOM 录入、流程梳理这些脏活 Agent 只能辅助；且实施周期长的主因往往是**企业自身尚未想清楚需求**，Agent 无法代替企业决策

**此条不得在对外材料中夸大。**

### 2.2 三条结论

**① 除 Rebuild 外，"ERPNext + AI" 方向最高 77 star。**
不是需求不真，是做法的天花板——所有项目都停在「加个聊天框调 API」。

**② Rebuild 是真正的对手，但缺 ERP 深度。**
Java/SpringBoot，8 年积累，零代码建模 + 全图形化设计 + AI 助手 + Skills/工具/知识库/MCP，GPL-3.0 + 商业双许可。
它的弱点是结构性的：**「快速搭建 WMS/MES」= 表单 + 流程 + 审批，没有 GL、BOM、成本累加、库存估值这些十五年攒下来的事务内核。**
→ 这既是我们的护城河，也是必须守住的东西。若最终做成「又一个可配置表单平台 + AI 助手」，Rebuild 领先 8 年。

**③ ERPClaw 验证了需求，也证伪了「推倒重来」。**
从零重写 ERP（Python + SQLite/PostgreSQL），半年 92 star。基于 ERPNext 是正确选择。

### 2.3 空缺矩阵

| ERPNext + MCP 桥 | ✅ | ❌ | ❌ | ❌ |
| Rebuild | ❌ | ⚠️ | ❌ | ⚠️ |
| ERPClaw | ❌ | ✅ | ❌ | ❌ |
| KAI（已死） | ✅ | ⚠️ | ❌ | ❌ |

**空缺是真的，而且能看清它为什么空着：前两列容易，后两列难。而后两列恰好是 ERP 敢不敢让 agent 动手的前提。**

## 16. 许可与商业化

### 16.1 已决策

| 项 | 决策 | 日期 |
|---|---|---|
| 许可 | **GPL-3.0**（因依赖 ERPNext，兼容性上基本无第二选择） | 2026-08-19 |
| CLA | **不设** | 2026-08-19 |
| 双许可 | **放弃** | 2026-08-19 |

### 16.2 这个决策关闭了什么

不设 CLA 意味着**贡献者保留自己代码的著作权**。因此：

- ❌ **永久失去双许可能力。** 将来若想以商业许可分发，需逐一取得每位贡献者授权，实际不可行
- ❌ 无法把社区贡献的代码用于闭源产品
- ❌ Rebuild 走的「GPL-3.0 + 商业授权」那条路对本项目不再开放

**此决策不可逆，后续任何商业化提案不得以「补 CLA」为前提。**

### 16.3 这个决策换来了什么

- ✅ **贡献门槛最低。** CLA 是许多开发者拒绝贡献的直接原因
- ✅ **社区信任度最高。** 无「厂商随时可以闭源」的隐忧
- ✅ 与 ERPNext / Frappe 生态的价值观一致

### 16.4 剩下的商业化路径

均不依赖代码所有权，全部成立：

| 路径 | 说明 |
|---|---|
| 托管 / SaaS | 参照 Frappe Cloud 模式 |
| 实施与咨询 | 主数据整理、BOM 建模、流程梳理——恰是 Agent 替代不了的部分（§1.4.5） |
| 支持与 SLA | 企业级支持合同 |
| 培训与认证 | 实施顾问认证体系 |
| 行业包 | 内核 GPL，特定行业包可由生态伙伴独立提供 |

### 16.5 GPL-3.0 vs AGPL-3.0（已决策）

**GPL-3.0 的网络漏洞**：GPL 只在**分发**时触发回馈义务。他人可以拿本项目代码运行闭源 SaaS 而无需公开任何修改。对一个 ERP 项目而言，SaaS 正是最主要的使用形态。

**AGPL-3.0** 补上了这个漏洞（网络访问即视同分发）。GPLv3 §13 明确允许与 AGPLv3 代码结合，因此**本项目自有代码采用 AGPL-3.0、依赖的 ERPNext 保持 GPL-3.0，在许可兼容性上是可行的**（正式定稿前建议做一次法律核对）。

**代价**：AGPL 会让部分企业用户望而却步（不少公司有 AGPL 禁用政策），可能压低采用率。

**决策（2026-08-19）：采用 GPL-3.0，不采用 AGPL-3.0。**

理由：当前阶段**采用率远比防白嫖重要**。参照 §2.2，本赛道最大同类项目仅 1,054 star——真实风险是无人使用，而非被闭源 SaaS 白嫖。GPL-3.0 与 ERPNext / Frappe 生态一致，对社区阻力最小。

**此项与 CLA 同样不可逆**（无 CLA 时变更许可需全体贡献者同意），后续不得以「改用 AGPL」为前提做商业化假设。
