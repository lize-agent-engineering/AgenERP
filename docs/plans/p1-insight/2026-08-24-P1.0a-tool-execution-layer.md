## 0. 为什么单独立项

P0.2 交付的是**契约声明**：10 个 `ToolContract` 对象，各带前置条件、后置断言、
返回裁剪规则、风险等级。判据是 `pytest tests/contracts -q` 退 0（151 条），
验的是**声明本身的合法性与门禁挂载**。

**它们没有可执行体。** `QUERY_READ` 是一个 dataclass，不是一个能打站点的函数。

> **判据与交付是吻合的**，P0.2 没有欠账——欠的是**下一层**。
> 之所以现在才发现，是因为 P1.0 是第一个真要**跑**这些工具的工作项。

`docs/architecture/module-boundaries.md` §7.6 对这件事已有明写：
「接活站点的 B 半未做，工作项 4 因此仍是 `planned`，不是 `done`」。**本 plan 就是那个 B 半。**

## 2. 核心原则：执行体照抄契约，不自己发明

**契约里已经把踩过的坑逐条写死了。** 执行体的任务是**实现它们**，
不是重新发现它们。逐条摘录（这些是后置断言/裁剪规则的原文，不是本 plan 的新主张）：

**`permission.scope`**
> 必须逐个调 `frappe.has_permission`，**不能从 DocPerm / Custom DocPerm 表反推**
> ——反推版漏报了 `Sales Invoice`，而该用户明明读得到；**漏报比噪声更危险**
>
> 必须按 app 过滤掉 Frappe 框架自身的 DocType——不过滤时老板 83 个、工人 61 个，
> 九成是 Token Cache / Desktop Icon 这类管道

**`lineage.trace`**
> 必须扫**子表级** Link 字段——实测 21 个指向 `Sales Order` 的 Link 里 **14 个在子表**，
> 只扫主表会返回空结果
>
> 子表命中必须**回溯到父单据**，否则返回的是明细行而不是单据

**`doc.links`**
> 下游筛选规则是「排除已取消（`docstatus == 2`）」，**不是**「只要已提交」——
> **草稿下游同样是证据，滤掉它会把 L2 门禁架空**

**`system.overview`**
> 必须给出公司名——实测中缺它导致模型把公司名当客户名查，白费 2–3 次调用

**`query.read`**
> 返回的每一行都必须来自调用方声明的 DocType，**不得跨表拼装**
> 剥离 `modified` / `creation` / `owner` / `_comments` 等框架管道字段

## 3. Goals

1. `agenerp/tools/` 下 10 个执行体，各自打 ERPNext REST 面
2. **一个统一的执行入口**：跑前查前置、跑后查后置、按 `returns` 裁剪、
   按 `module-boundaries.md` §7.5 包裹数据边界标记，
   任一环失败按契约的 `on_violation` 处置（全部是 `abort_and_report`）
3. 站点上有一个**受限用户**，使 `permission.scope` 的判别力有真实的反例可验
4. 判据两层：单测（假站点，`tests/tools/`）+ 活站点合规判据；外加一条契约↔执行体的双向注册判据

## 4. Non-Goals

- **不**实现控制循环（那是 P1.0 的 T2）
- **不**实现写工具（P2 以后，且受 L2 门禁约束）
- **不**实现 §7.4 的「连续 N 次权限拒绝即终止循环」——那是循环的行为，不是工具的
- **不**优化性能——先正确，`max_rows` 已经把返回量框住了
- **不**碰 `permission.scope` 的**开场自动注入**（那是编排行为，属 P1.3）
- **不**创建或修改 `tests/gates/**` 下的任何文件（红线 1），**不**改 `.github/workflows/**`（红线 2）、
  **不**改 `docs/masterplan/` 已有行（红线 3/5，STATE 只追加）——见 §5.1

### 5.1 一处红线冲突及其处置（评审期确认，不由执行者临场判断）

WBS §4 第 78 行把 **🔴 `tests/gates/test_tool_execution_live.py`** 写成 P1.0a 的判据之一。
但：

- 红线 1：`git diff` 触及 `tests/gates/**` → **立即停机**（AGENTS.md 前言表第 1 行）。
- CI `gates.yml` 的 `gates-untouched` job 对同一路径复核，缺 `Gates-Change-Approved-By:` trailer 即红。
- 优先级次序（AGENTS.md 前言）：**红线 > `docs/masterplan/` 的执行协议**。

→ **执行者不得创建该文件。** 处置如下，三条都是本 plan 的硬约束：

1. 同样的断言由执行者写在**非保护路径** `tests/tools/test_live_conformance.py`，
   内容即是将来那个门禁文件的内容，**断言强度不得因为换了路径而降低**。
2. 把它提升进 `tests/gates/` 并接进 CI，是**人的动作**（需 `Gates-Change-Approved-By:` trailer；
   改 CI 配置本身也受红线 2 与 `01-EXECUTION-MODEL.md` §「禁止④」约束）。
   本 plan 在 Phase 4 把这件事**追加**进 STATE §3 needs-human 队列，附文件路径与提升方式。
3. 本 plan 收口时**只认自己交付的那一半**：`pytest tests/tools -q` 的退出码 +
   活站点合规判据的退出码 + commit sha。**不得声称 WBS §4 的 🔴 判据已满足**——
   它的门禁那一半在人动手之前始终未满足。

## 6. Infrastructure And Config Prereqs

- **活站点 `frontend`**：`docker compose up -d` 起栈，种子数据集已装载（P0.8 已完成）。
- **站点凭据**：`client_from_env` 读 `AGENERP_*` 环境变量；缺凭据时它会**指名缺哪个变量**并抛
  `SiteError`。凭据存 `.env`（已 gitignored），**绝不进 git**。
- **受限用户由代码建，不由手工建**：CI 的 live job 每次都是**全新栈**，手工在本机站点上点出来的用户
  在那里不存在，合规判据会因此不可复现。故 Phase 1 的受限用户必须是**幂等的装载步骤**
  （与 `agenerp/seedsite.py` 同一形态：跑两遍第二遍「新建 0」）。
- **单测不依赖站点**：`tests/tools/` 的假站点经 `agenerp/site.py` 的 `Transport` 协议注入，
  不起容器、不连网络，故 `pytest tests/tools -q` 在无凭据环境下也必须能全绿。
- **活站点合规判据在无凭据时 skip 而不是 fail**：它是「有站点才能跑」的那一层，
  但 skip 的理由必须打印出来，不得静默跳过。
- 回滚策略：执行体全是只读契约，**不写业务数据**；唯一的站点写入是 Phase 1 的受限用户与角色，
  删除该用户即回滚。其余可回滚面是 git。

## 8. 已知风险

**① `permission.scope` 的服务端函数——已探，路通，但判别力未验。**

2026-08-24 活站点实测：

```
✓ frappe.client.has_permission {"doctype":"Sales Order","perm_type":"read"} → {"has_permission": true}
✗ frappe.permissions.has_permission → HTTP 403 PermissionError（不在白名单）
```

→ 走 **`frappe.client.has_permission`**，路是通的。

⚠️ **但「它会不会正确地返回 False」尚未验证**：站点上目前只有 Administrator，
它对什么都有权限，所有调用都回 `true`。一个永远返回 `true` 的实现与正确实现
在当前站点上**长得一模一样** —— 这正是 CP9 继承项①那个形状。

→ 已转成 Phase 1 的受限用户项与 Phase 2 的「真反例」判据，**不留作风险自生自灭**。
STATE §3 第 265 行同时记着「这件事 loop 可以自己做，不需人定」。

**② 后置断言里有些是「过程约束」而非「结果约束」。**
例如 `permission.scope` 的「必须逐个调 `has_permission`」——从返回值看不出来。
这类断言只能靠**实现方式**保证，判据得验实现（断言请求序列），不能只验返回。

→ 已转成 Phase 2 的「请求序列断言」项。**照实登记：这类断言比结果型断言弱**——
它验的是「发了 N 次请求」，验不了「每次都用对了参数语义」。这条残留风险不消除，见 §9。

**③ `schema.search` 的向量兜底不在本期。**
`docs/design/context-and-memory.md`「② 的实现方式已被 Spike 07 修正」段的结论是
「结构化导航优先，向量检索降级为兜底召回」（同一结论在
`docs/architecture/open-questions.md` U6 / 第 14 行记为 §8.1，Top-5 最好仅 75%）。
本期实现到关键词/结构化匹配。**不为一个未证实需要的能力先建索引**——重开条件见 §9。

**④ 本期的判据跑不进 CI。**
CI 的 `unit-and-contracts` job 只跑 `tests/unit` 与 `tests/contracts`，`lint` job 的 ruff
路径同样不含 `tests/tools`。把它们接进去是**改 CI 配置**，受红线 2 与
`01-EXECUTION-MODEL.md` §「禁止④」约束，只能由人做（与 §5.1 的交接同一批）。

→ 后果照实登记：本 plan 收口时的绿是**本机的绿**，`docs/plans/00-plan-authoring-and-execution-guide.md`
