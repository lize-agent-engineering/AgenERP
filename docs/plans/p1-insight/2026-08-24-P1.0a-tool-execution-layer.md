## 0. 为什么单独立项

P0.2 交付的是**契约声明**：10 个 `ToolContract` 对象，各带前置条件、后置断言、
返回裁剪规则、风险等级。判据是 `pytest tests/contracts -q` 退 0（151 条），
验的是**声明本身的合法性与门禁挂载**。

**它们没有可执行体。** `QUERY_READ` 是一个 dataclass，不是一个能打站点的函数。

> **判据与交付是吻合的**，P0.2 没有欠账——欠的是**下一层**。
> 之所以现在才发现，是因为 P1.0 是第一个真要**跑**这些工具的工作项。

## 1. Current Baseline（实读，2026-08-24）

10 个契约都在 `agenerp/tools_readonly.py`，各自的约束已写死：

| 工具 | max_rows | 裁剪规则 | 前置 | 后置 |
|---|---|---|---|---|
| `query.read` | 200 | 2 | **3**（L1/L2/L3 门禁）| 1 |
| `snapshot.read` | 500 | 2 | **3**（同上）| 1 |
| `schema.search` | 10 | 2 | 0 | 1 |
| `lineage.trace` | 100 | 2 | 0 | **3** |
| `rule.lookup` | 50 | 1 | 1 | 1 |
| `system.overview` | 40 | 2 | 0 | 2 |
| `permission.scope` | 60 | 1 | 0 | 2 |
| `doc.get` | 1 | 2 | 0 | 1 |
| `doc.links` | 100 | 2 | 0 | 1 |
| `meta.fields` | 200 | 2 | 0 | 1 |

前置为 3 的两个是**作答类工具**（`ANSWERING_TOOLS`）——门禁挂在它们身上，
因为它们的返回值就是答案里的数字。

## 2. 核心原则：执行体照抄契约，不自己发明

**契约里已经把踩过的坑逐条写死了。** 执行体的任务是**实现它们**，
不是重新发现它们。逐条摘录（这些是后置断言/裁剪规则的原文，不是本 plan 的新主张）：

**`permission.scope`**
> 必须逐个调 `frappe.has_permission`，**不能从 DocPerm / Custom DocPerm 表反推**
> ——反推版漏报了 `Sales Invoice`，而该用户明明读得到；**漏报比噪声更危险**
>
> 必须按 app 过滤掉 Frappe 框架自身的 DocType——不过滤时老板 83 个、工人 61 个，
> 九成是 Token Cache / Desktop Icon 这类管道

**`lineage.trace`**
> 必须扫**子表级** Link 字段——实测 21 个指向 `Sales Order` 的 Link 里 **14 个在子表**，
> 只扫主表会返回空结果
>
> 子表命中必须**回溯到父单据**，否则返回的是明细行而不是单据

**`doc.links`**
> 下游筛选规则是「排除已取消（`docstatus == 2`）」，**不是**「只要已提交」——
> **草稿下游同样是证据，滤掉它会把 L2 门禁架空**

**`system.overview`**
> 必须给出公司名——实测中缺它导致模型把公司名当客户名查，白费 2–3 次调用

**`query.read`**
> 返回的每一行都必须来自调用方声明的 DocType，**不得跨表拼装**
> 剥离 `modified` / `creation` / `owner` / `_comments` 等框架管道字段

## 3. Goals

1. `agenerp/tools/` 下 10 个执行体，各自打 ERPNext REST 面
2. **一个统一的执行入口**：跑前查前置、跑后查后置、按 `returns` 裁剪，
   任一环失败按契约的 `on_violation` 处置（全部是 `abort_and_report`）
3. 单测（假站点）+ **活站点门禁**各一层

## 4. Non-Goals

- **不**实现控制循环（那是 P1.0 的 T2）
- **不**实现写工具（P2 以后，且受 L2 门禁约束）
- **不**优化性能——先正确，`max_rows` 已经把返回量框住了
- **不**碰 `permission.scope` 的**开场自动注入**（那是编排行为，属 P1.3）

## 5. Task Route

### T1 · 统一执行入口
`agenerp/tools/runtime.py`：

```
execute(tool_name, params, client, context) →
    ① 查前置（check_preconditions）——不满足则 abort_and_report，**不发请求**
    ② 打站点
    ③ 按 returns 裁剪（must_keep 保留、max_rows 截断、trim_rules 落实）
    ④ 查后置（check_postconditions）——不满足则 abort_and_report
```

**③ 与 ④ 的顺序不可颠倒**：后置断言判的是**给出去的东西**，先裁后判才对得上。

### T2 · 10 个执行体
按依赖排：`system.overview` → `meta.fields` → `doc.get` → `doc.links` →
`query.read` → `lineage.trace` → `snapshot.read` → `permission.scope` →
`schema.search` → `rule.lookup`

`rule.lookup` 的前置是「行业包已加载」——P1.6 之前**没有行业包**，
故它的执行体本期只实现到「前置不满足 → 明确报错」，**不伪造一个空包**。

### T3 · 判据两层

**单测**（假站点，`tests/tools/`）：每个工具至少三条——
正常返回、裁剪生效、后置违规时 abort。

**活站点门禁**（🔴 `tests/gates/test_tool_execution_live.py`）：
每个工具在活站点各跑一次，断言**返回形状合约束**：

```
must_keep 的字段都在
行数 ≤ max_rows
框架管道字段（modified/creation/owner/_comments）已剥离
```

> ⚠️ **判据不许只验「调得通」。** 「调得通」与「守约」是两件事，
> 而后者才是契约存在的理由。这是 CP9 继承项①（退出码 0 不是充分判据）
> 在这一层的具体形态。

### T4 · 一条反向判据：契约与执行体不许各说各话
断言**注册表里每个契约都有执行体、每个执行体都有契约**，双向。
少一边就红——避免「加了工具忘了契约」或反过来。

## 6. 已知风险

**① `permission.scope` 的服务端函数——已探，路通，但判别力未验。**

2026-08-24 活站点实测：

```
✓ frappe.client.has_permission {"doctype":"Sales Order","perm_type":"read"} → {"has_permission": true}
✗ frappe.permissions.has_permission → HTTP 403 PermissionError（不在白名单）
```

→ 走 **`frappe.client.has_permission`**，路是通的。

⚠️ **但「它会不会正确地返回 False」尚未验证**：站点上目前只有 Administrator，
它对什么都有权限，所有调用都回 `true`。一个永远返回 `true` 的实现与正确实现
在当前站点上**长得一模一样** —— 这正是 CP9 继承项①那个形状。

→ **T2 实现 `permission.scope` 时必须先建一个受限用户**（例如只读某几个
DocType 的「车间工人」角色），否则它的判据是空的。这条写进 T2 的前置。

**② 后置断言里有些是「过程约束」而非「结果约束」。**
例如 `permission.scope` 的「必须逐个调 has_permission」——从返回值看不出来。
这类断言只能靠**实现方式**保证，判据得验实现（例如断言请求序列），
不能只验返回。**照实登记：这类断言比结果型断言弱。**

**③ `schema.search` 涉及向量检索**，而 §8.1 的结论是「结构化导航优先，
向量仅作兜底召回」。本期实现到**关键词匹配**即可，向量兜底留到有真实
召回质量问题时再说——不要为一个未证实需要的能力先建索引。
