## 5. 设计

### D1 · 四步本体用 Python，`scripts/verify-gitops.sh` 是薄壳

**备选**：B 全写在 shell 里（照 WBS 字面）· C 全做成 pytest。

**否 B**：四步的断言都是「字段**真的**在/不在那个站点上」，shell 里那要靠 `grep` JSON，
脆且失败时说不清哪一步坏的；而 `apply_pack` / `SiteClient` 全在 Python 里。
薄壳照样满足「`verify-gitops.sh` 退 0」的字面。

**否 C**：GitOps 是**流程**不是单元；pytest 形态会诱使我把「建站」塞进 fixture，
那一步失败时长得像「测试跳过」——而一条会 skip 的判据等于一条不存在的判据。

### D2 · 只实现 `creates`，`updates` 继续显式抛

有调用方的只有 `creates`（第四步）。`updates` 今天仍然没有调用方 ⇒ **照 YAGNI 不做**，
且**保持显式抛而不是静默跳过**（P0.5 那条纪律不改）。
同一条 deferred 的重开条件对 `updates` 原样保留。

### D3 · 建字段**不放宽方向不变量**

`_assert_direction` 那条「建 = 只在包里」的不变量是接上真删除之后**挡住灾难性误删的最后一道闸**
（`apply.py:130` 逐字：不用裸 `assert`，因为 `python -O` 下它整条消失）。
实现 creates **不动它一行**。

### D4 · 探针用 `ToDo`，不用 `Item`

`gitops.test` 没有 erpnext ⇒ `Item` 在那边不存在。用 frappe core 的 `ToDo`。
⚠️ **代价**：与 P0.5 那条门禁（用 `Item`）不是同一张表，两者**互不替代**。
