## 0. 人的提议比我的好，先说清楚为什么

我原本要做的是「**候选清单里补一列『某某的子表』**」—— 那是继续修补**一次性问答**。
人提的是「**给 agent 查询工具，让它自己去找**」。

**后者才是 owner doc 说的主路。** `§8.1` 修正后的 ② 逐字：

> ② schema 元知识 → **优先结构化导航**（`system.overview` / `meta.fields` / `doc.links`）；
> 向量检索仅作**兜底召回**。

而 **Spike 02 的受约束 Agent 四道探针全部通过，全程零向量检索**，用的正是这三个工具。
⇒ **前五轮一直在优化兜底召回；第五轮补了「模型定夺」这一半；本轮才轮到「结构化导航」本身。**

**而且工具仓里现成就有**（`agenerp/tools/registry.py` 十个执行体、
`agenerp/explain/loop.py` 677 行的控制循环、失控闸、成本台账）—— **不用造轮子。**

## 1. Current Baseline

| 轮 | 做了什么 | Top-1 | **Top-5** |
|---|---|---|---|
| 4 | 纯向量 `text-embedding-v4` | 50.0% | **70.0%** |

| — | oracle（**上限**） | 75.0% | **92.5%** |

第五轮 L2 的 4 条错里 **3 条是父表/子表分不清**，而候选清单里**没有任何一处**
告诉模型谁是谁的子表 —— 尽管 `tests/dsl/fixtures/child-tables.json`（活站点导出）
和 `SchemaView.child_doctype()` 仓里现成就有。

## 1.1 🔴 预算：这一轮的风险不在准确率，在成本

`loop.py` 写着 **D-26 定的 20 万 token / 次**上限。
**40 条 × 20 万 = 800 万 token 的最坏情况** —— 那个循环是为「一次解释一个问题」设计的，
不是为 40 条评测扫。P1 有过一次单问答烧掉 **13.6 万** 的实测。

⇒ **本轮强制「先探再跑」**，闸口写死在 §2.0。

## 2. 事先写死的判据与预测

### 2.0 🔴 预算闸：先探 3 条，量出真实单价，再决定跑不跑全量

**探针配置**：`max_turns=8`（默认 40，刻意收紧到 1/5 —— 找一个字段不该要 40 轮）。

**闸口（事先写死，不许事后放宽）**：

| 探针实测单价 | 决定 |
|---|---|
| **≤ 8k token/条** | 跑全量 40 条（预算 ≤ 320k），继续 §2.2 |
| **8k – 20k/条** | **只跑 20 条**，并在结论里写明 n 减半 |
| **> 20k/条** | **不跑全量**。记下单价，本轮到此为止，交人决定 |

⚠️ **单价按 API 回的数算，不是我估的。**

### 2.1 Arm A（便宜的对照，先跑）· 候选清单补一列「某某的子表」

第五轮那套原样不动，只在候选行尾加 `（<父表> 的子表）`。约 32k。

**A1 · 模型选单据准确率从 90.0% 升到 **≥ 95%**（4 条错里 3 条是父/子混淆，修掉应见效）。
**A2 · 合成 Top-5 落在 **85%–92.5%**（上限仍是 oracle）。

### 2.2 Arm B（人提的那件事）· 给 agent 工具，让它自己查

复用 `agenerp/explain/loop.py` 与现成的十个执行体，
**不新写工具**（`system.overview` / `meta.fields` / `doc.links` / `schema.search` 都在）。

**B1 · 设施自检：agent 至少调到过 `meta.fields` 或 `system.overview`**
—— 若它一次工具都不调、直接凭记忆答，本轮测的就不是「结构化导航」，而是「模型背没背过 ERPNext」。
**这一格不过，后面的数一概不看。**

**B2 · 🔴 决定性一格：Arm B 的字段 Top-5 落在 **75%–95%**。**
下沿刻意低于第五轮的 82.5% —— **我不预设 agent 一定更好**：
多轮自由探索也可能比「一次给 50 个候选」更容易跑偏。

**B3 · Arm B 的答案**必须能指回真实存在的字段**（硬约束 ④）——
指不回的一律判未命中，**不给「它意思对了」这种分**。

### 2.3 判定标准（事先写死）

| 结果 | 判定 |
|---|---|
| **B2 ≥ 90%** | 🔴 达到验收线 ⇒ ⚠️ **仍不判过**，须先换一份不是我出的评测集复测 |
| **B2 > A2** | **结构化导航赢了喂候选** ⇒ 主路定为工具导航，Arm A 降级为兜底 |
| **A2 > B2** | **喂候选赢了自由导航** ⇒ 这会**反驳 §8.1 那句「优先结构化导航」**，须照实记并交人重判 owner doc |
| 两者都 < 85% | 都不够，回判定表 |

⚠️ **本轮不实现任何东西**，`agenerp/**` 一个字不动（只读地复用它）。

## Closure（2026-08-28 · P2 收口审查补记）

**Status: `superseded` —— 不是「没做完」，是它的判据在执行途中被换掉了。**

### 发生了什么

本 plan §2.3 的判定表整张写在 **Top-5** 口径上（`B2 ≥ 90%` / `B2 > A2` / …）。
而**人 2026-08-27 把 P2.0R 的验收判据改了**（`DECISIONS.md` D-28，WBS §5 P2.0R 行逐字
「人 2026-08-27 裁定改判据」）：从 Top-5 改成**任务完成率 ≥95%**，
判据文件也换成了 `tests/gates/test_schema_field_task_completion.py`。

P2.0R 随后在 **2026-08-28 由人按新判据判过**（D-29：独立评测集 60 条全跑、一道闸不设、
**57/60 = 95.0%**，`deepseek-v4-pro-0813`）。

⇒ **本 plan 的判定表从那一刻起就不再拥有收口权。**

### 它提的方向**确实落地了**（这一点不含糊）

本 plan 的主张是「从**喂候选**改成**给工具、让 agent 自己导航**」。
那正是今天在产品里跑着的形态：`schema.search` + `meta.fields` 是 P2.0R 最终的主力，
也是 P2.3 视图 Agent 的工具面（`agenerp/views/loop.py` 的 `VIEW_TOOLS`）。
**方向没作废，作废的是「用 Top-5 这把尺子量它」。**

### 13 个未勾项的去处（反怠工条款要求逐条有着落）

全部标为 `[~]` = **随判据更换移出范围**，理由同一条：
它们是**对着 §2.3 那张 Top-5 判定表**的记账（A1/A2/B1/B2/B3 的「预测/实测/吻合与否」、
探针单价与闸口、只走 §2.3 判定、落 §8.1）。判据换掉之后，
**照原表记账既得不出结论，也不是任何人要的结论**。

⚠️ **不是「做了但没勾」，是「不做了，且说清为什么」** —— 这个区别要写明，
免得后来人以为有一批实测数据没落盘。

### 残余风险

本 plan 写的 A/B 对照（喂候选 vs 自由导航）**最终没有以对照实验的形态跑完**。
今天「结构化导航优先」这句话的支撑是 **D-29 的任务完成率**，
**不是**本 plan 设计的那次 A/B 比较。⇒ owner doc §8.1 那句「优先结构化导航」
今天的证据是「按新判据达标」，**不是「实测赢过喂候选」**。这一点照实记，不许被读成后者。

**重开条件**：若将来要回答「喂候选到底比不比自由导航差」，本 plan 的 A/B 设计仍然可用，
届时重开并换一张与当时判据一致的判定表。
