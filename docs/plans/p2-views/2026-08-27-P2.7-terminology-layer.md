## 1. Current Baseline（实读，2026-08-27 @ `2ecf2f8`）

### 1.1 🔴 整站 6350 个业务字段，label 含中文的是 **0**

不是「少」，是**零**。抽样看得更清楚：

| 字段 | 现在的 label |
|---|---|
| `Item Reorder.warehouse` | 「**Request for**」 |
| `Item Default.buying_cost_center` | 「Default Buying Cost Center」 |
| `Work Order.qty` | 「Qty To Manufacture」 |

第一条尤其说明问题：**字段名说的是仓库，标签说的是「请求给」。**
一个中国工人看着这张表，既读不懂英文，也猜不出这一列到底是什么。

### 1.2 Spike 07 给术语层加的第二个理由

`${XM}/spike/07-schema-retrieval/FINDINGS.md` §6.3 逐字：

> §10 的术语层原本是为了修「大师」「进行中」这类翻译事故。本次实测给它加了第二个理由：
> **术语层同时是检索质量的前置条件。** 字段有了准确中文标签之后，
> 无论结构化导航还是向量检索都会更准。

⚠️ 那是 Spike 07 的**建议**，不是实测结论。本轮 §11 会量一次，**但它不参与本项的过/不过**。

### 1.3 P2.0R 三轮之后，术语层在候选里的位置变了

第三轮钉住的那句话：**「任何不引入新信息的重排，结构上都够不着那 35 个点」**。
已被推翻的两个机制（族聚合、分数融合）共同点是**从同一批 embedding 再算一遍**。
**术语层不同 —— 它往索引里注入了这批向量里原本没有的信息。**

⚠️ **这不是选路**（D-16）。它只说明「量一下它值不值」是有理由的，见 §11。

### 1.4 载体

P2.0 已判：产物落 AgenERP 自有表。建表与 GitOps 是 P2.4 的结果面 ⇒
v0 落成仓内的 JSON 产物 + 一个加载器，**并在代码里写明这是暂时的**（形态同 `agenerp/dsl/roles.py`）。

## 2. 事先写死的判据与预测

### 2.0 范围：**跟着路线 C 走**，只做车间工人那 15 张表 / 317 个字段

理由两条：
1. **与 P2.2 一致** —— 路线 C 的分母就是这个。
2. **成本**。整站 6350 个字段是 20 倍量。P1 有过一次单问答烧掉 13.6 万 token 的实测，
   本仓的规矩是**有真跑判据前先算账**。

### 2.1 成本预算（先算账，D-17）

**首选本地 Ollama，API 成本 = 0。** 本机实测有 `qwen3.5:0.8b` / `qwen3:14b` / `qwen3:0.6b`。

⚠️ **若本地模型质量不过 T3 那一关，才升级到 `qwen3.6-plus`**（CI 那把 secret 现用的就是它）。
届时的账**先算再跑**：317 个字段按 20 条一批 ≈ 16 次调用，
每次约 800 in / 400 out ⇒ 合计约 **13k in / 6.4k out**。
**这是那次 13.6 万的十分之一，可承受** —— 但**只在本地不够时才花**。

### 2.2 T1 · 覆盖率 = **100%**（317/317 每个字段都有一条），且**逐条指回真实字段**

硬约束 ④ 用在术语层自己身上：一条指不回真实字段的术语，是纯粹的噪音。

### 2.3 T2 · 生成的 label **≥ 95%** 含中文字符，且**不等于**英文原 label、**不等于** fieldname

这三条都是**规则面**（硬约束 ③），不许交给模型判。

### 2.4 T3 · 🔴 决定性一格 · **15 条「不该错」清单**，预测 **≥ 13/15 命中**

**清单与可接受关键词在跑之前写死如下**，事后不许调：

| 字段 | 可接受的 label 里必须含以下任一 |
|---|---|
| `Item.item_code` | 编码 · 编号 · 代码 · 料号 |
| `Item.item_name` | 名称 |
| `Item.stock_uom` | 单位 |
| `Item.description` | 描述 · 说明 |
| `Item.brand` | 品牌 |
| `Work Order.qty` | 数量 |
| `Work Order.produced_qty` | 数量 · 产量 |
| `Work Order.status` | 状态 |
| `Work Order.company` | 公司 |
| `Work Order.source_warehouse` | 仓库 |
| `Stock Entry.posting_date` | 日期 |
| `Stock Entry.from_warehouse` | 仓库 |
| `Stock Entry.to_warehouse` | 仓库 |
| `Stock Entry Detail.qty` | 数量 |
| `Stock Entry Detail.uom` | 单位 |

⚠️ **这是一条弱判据，说清它弱在哪**：它验的是「有没有离谱地错」，
**不是「翻译得好不好」**。后者没有规则面的判法 —— 而**我不打算让模型判自己**（硬约束 ③）。
⇒ **术语层的质量上限由这条判据决定，且这个上限是低的。这句话必须写进 owner doc。**

### 2.5 判定标准（事先写死）

| 组合 | 判定 |
|---|---|
| T1 ✅ 且 T2 ✅ 且 **T3 ≥ 13/15** | 术语层 v0 可用，**P2.7 过** |
| T3 **< 13/15** | **换模型重跑**（先本地大一档，再考虑 `qwen3.6-plus`，且先算账）；仍不过则本项不过 |
| T1 或 T2 ❌ | 生成流程有问题，修完重跑 |

⚠️ **不得靠调可接受关键词去凑 T3。** 清单在 §2.4 写死并先于生成提交，git 可查。
