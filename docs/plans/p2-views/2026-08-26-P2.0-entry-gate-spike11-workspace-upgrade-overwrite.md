## 0. 这个实验要回答什么

**承重命题**：*视图产物落 Frappe 的标准 `Workspace`，还是落 AgenERP 自己的表？*

它承重在于：若「改标准 Workspace 会被 app 升级静默覆盖」成立，则整个 P2 的视图 DSL
**必须存在 AgenERP 自己的表里**，不参与 Frappe 的 fixture 覆盖循环；否则视图 Agent 的产物
**寿命只有一次升级**。反之若证伪，Workspace 才重新进入载体候选。

**不回答**：行为层（按钮点了干什么）能不能落 Workspace —— `view-dsl-and-eval.md` §10.4
已实测「不能」，与本实验无关，不得混判。

### 1.2 Workspace 确实走 fixture 同步

`apps/frappe/frappe/model/sync.py:29` 的 `IMPORTABLE_DOCTYPES` 含 `("desk", "workspace")`；

站点上的标的：`apps/erpnext/erpnext/selling/workspace/selling/selling.json`，
`doctype=Workspace` · `name=Selling` · `public=1` · **`modified = 2023-07-04 14:35:58.204465`**。

### 1.3 覆盖动作确实是「整条记录删了重插」

`import_file.py:230-239`：`if frappe.db.exists(...): delete_old_doc(...)` → `doc.insert()`。
`delete_old_doc`（:258-276）里 `frappe.delete_doc(..., force=1, for_reload=True)`。

**没有字段级合并层**，且旁证极强：

```python
ignore_values = { ..., "Workspace": ["is_hidden"] }   # import_file.py:30-37
ignore_doctypes = [""]                                # :39
```

⇒ 覆盖时**只有 `is_hidden` 一个字段**从旧记录抄回来；`ignore_doctypes` 是空的，
所以**没有任何子表**（shortcuts / links / charts / number_cards）被保留。
Frappe 上游自己手挑了恰好一个字段去豁免 —— 这本身就说明它清楚这个覆盖是破坏性的。

### 1.4 ⚠️ **source-of-truth 冲突：`module-boundaries.md` §11.4 的机制陈述对 Workspace 不成立**

§11.4 逐字写着：

> `frappe/modules/import_file.py` **按文件 md5 决定是否导入**：
> 日常 `bench migrate`：hash 未变 → 跳过（**:137**）→ 用户改动存活
> 升级 ERPNext 且官方改过该 JSON：hash 变化 → `import_doc` 走 `delete_doc` + 重新插入（:273）

**`:273` 那一半是对的**（v15 落在 :274，v16 落在 :273，同一行 `frappe.delete_doc`）。
**`:137` 那一半，对 `Workspace` 不成立。** 实读 `import_file.py:130-144`（v15；v16 :128-141 结构逐行相同）：

```python
if not force and db_modified_timestamp:
    stored_hash = None
    if doc["doctype"] == "DocType":                     # ← 只有 DocType 才去取 hash
        stored_hash = frappe.db.get_value(doc["doctype"], doc["name"], "migration_hash")
    if stored_hash and stored_hash == calculated_hash:  # ← :139(v15)/:137(v16)，Workspace 永不进这支
        continue
    if is_db_timestamp_latest and doc["doctype"] != "DocType":   # ← Workspace 真正的闸门
        continue
```

`migration_hash` 是 **`DocType` 的字段**，`Workspace` 没有。⇒ 对 Workspace 而言
`stored_hash` **恒为 `None`**，md5 算了但**从不参与判断**。
真正的闸门是 `is_db_timestamp_latest` = DB 里的 `modified` **是否不早于** JSON 里的 `modified`。

**这件事直接影响 `REF:ROADMAP-SPIKE1112` 写死的证伪判据。** 该判据逐字是：

> 改 Workspace → 手改 app 内该 JSON **使 md5 变化** → `bench migrate` → **改动仍在即证伪**

⇒ **照字面执行，几乎注定得到「证伪」，而那个「证伪」是假的**：改动之所以活着，
不是因为 Frappe 保护了它，是因为**这条判据拧的是一个对 Workspace 不接线的旋钮**。

> 这正是 P1 复盘 §1.2 那件事的同形：**判据绿 ≠ 判据在测它名字说的那件事。**
> 差别只在于这次是在**跑之前**发现的。
>
> ⚠️ 判据是裁判，**本文不改它**。处置办法是 §2 的双臂设计：
> **字面判据照跑（Arm A），并另跑一臂真实升级形态（Arm B），两臂结果并列上报，由人裁定。**

## 2. 事先写死的假设（CP9 继承项 ②：预测在前、结果在后、逐条吻合）

**用户改动**统一定义为对 `Workspace/Selling` 做三件事，一次做完：
① 追加一条 shortcut，`label = AGENERP-SPIKE11-CANARY`（子表行）
② 改 `icon` 为一个可辨识值（普通字段）
③ 置 `is_hidden = 1`（**`ignore_values` 白名单里的那个字段**，作为同批对照）

### H1 · Arm C（控制组）：不动 app JSON → `bench migrate` → 改动**仍在**（①②③ 全在）

若不成立，说明 migrate 无条件重导，实验设施本身有问题。

### H2 · Arm A（`REF:ROADMAP-SPIKE1112` 的字面四步）：改 JSON **使 md5 变化但 `modified` 保持 `2023-07-04 14:35:58.204465` 不动** → `bench migrate` → 改动**仍在**

**这一格若如预测为真，按字面判据即为「证伪」。§2.3 事先声明它不算证伪。**

### H3 · Arm B（真实升级形态）：改 JSON **且把 `modified` 推到晚于 DB 的 `modified`** → `bench migrate` → 用户改动**消失**，`Workspace/Selling` 回到 JSON 原样

### H4 · 字段级隔离不存在：H3 发生时，**只有 `is_hidden`（③）幸存**，①②全灭

且 ① 那条 shortcut 在 `tabWorkspace Shortcut` 里是**物理删行**，不是标记隐藏
（`select count(*) ... where parent='Selling' and label='AGENERP-SPIKE11-CANARY'` → `0`）。

### H5 · md5 对 Workspace 惰性的直接证据：`Workspace` 无 `migration_hash` 字段

`frappe.db.has_column("Workspace","migration_hash")` → `False`（或等价查询为空）。

### H6 · 「静默」成立：H3 那次 `bench migrate` 的 stdout/stderr 里**不出现**任何指名 `Selling` 被覆盖 / 用户改动被丢弃的告警

### 2.3 ⚠️ 事先声明：为什么 H2 为真不算证伪

因为 H2 的手法**没有触到 Workspace 的闸门**（§1.4）。一个没接线的旋钮拧到底也不亮灯，
不能据此说灯是坏的。**这句话写在跑之前，不是跑完之后的辩解。**
