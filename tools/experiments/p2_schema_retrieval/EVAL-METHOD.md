# P2.0R 的评测方法 —— 重建版

> 2026-08-27。**这份文档存在的原因是我把前六轮做错了。**
> 人指出「生产标准是**任务完成率 ≥95%**」，而我用了六轮 **Top-5 召回率**，
> 并指出我对 Agent 开发/调试/优化的理解不够。学了 `eval-engineering`
> 与 LangSmith 的 `evaluation-approaches` 之后自查，**四条方法学缺陷全部坐实**。

## 一、旧那套错在哪（逐条，可复算）

### ① 指标错了：Top-5 在**奖励撒网**

按 `verifier-design` 的「Test the decision boundary」跑六个 fixture ——
**这一步我之前一次都没跑过**。喂进去：

```
Job Card.a / Job Card.b / Job Card.total_completed_qty / Job Card.c / Job Card.d
旧评分器 → Pass ✅        方法论期望 → Fail（塞满候选碰运气）
```

不是评分器写错，是 **Top-5 按定义就该这么判** ⇒ **它奖励「不做决定」**。
而生产要的是 agent **敢承诺一个答案**。

> LangSmith 把 agent 评测分三类：**Final Response / Single step / Trajectory**。
> **我这六轮全是 Single step**（只判它选没选对字段），却当任务完成率在用。

### ② 验证器在给「agent 自己说的话」打分

`verifier-design` 逐字：「**Never trust an agent-written action list**」「Build from
final state」。而我的评分器是**正则解析 agent 的输出文本**。

### ③ `expected` 是我猜的单点答案 ⇒ **已确认一次假拒**

`Job Card Time Log.completed_qty`（Float，标签「Completed Qty」）**真实存在**。
问句是「**工人报工**完成了多少数量」—— 报工记录本来就在时间日志上，
而 `Job Card.total_completed_qty` 是各条日志的**汇总**。
第五轮 agent 答了前者，**我判它错**。
`verifier-design` 逐字：「**Accept all equivalent valid results**」。

### ④ 没存 trace，失败无法归因

`calibration` 第一条是「Read complete runs」。而我的脚本连原始答案都没留 ⇒
第六轮那条「失败」（8 次模型调用、返回空）**至今无法归因**：
能力不足？Harness 缺陷？答案门禁拦的？查不了。

### ⑤ 一次动了两个变量

Arm A（关思考 + 一次性问答）→ Arm B（**开思考** + 工具导航），
`calibration` 要求「change **one** supported condition」。⇒ **那 +10 个点归因不成立。**

### ⑥ 一个已被证伪的结论，必须收回

我说过「即使单据消歧做到完美，**上限也只有 92.5%**」，还基于它推了整套
「要到 90% 需单据消歧 97.5%」。**Arm B 实测 95.0% 直接越过了它。**
⇒ 那不是任务的上限，是**我那条流水线的上限**。
**我把自己管道的天花板说成了问题的天花板。**

## 二、重建之后是什么样

### 指标：任务完成率（Final Response 口径）

**Agent 必须承诺一个字段。** 最后一行给多个 ⇒ 判「未承诺」，不替它挑。

### 验证器：三层，规则在前、判官在后

| 层 | 判什么 | 依据 |
|---|---|---|
| **1 规则** | 承诺了吗？字段在站点上**真实存在**吗？ | 硬约束 ④；`code settles objective facts` |
| **2 可接受集合** | 命中我事先列的等价答案 ⇒ 直接过，**不惊动判官** | reference-based |
| **3 判官** | 只判「这个字段**是否同样能回答该问题**」 | reference-free；`Use a judge only for semantic meaning` |

⚠️ **判官只在第 2 层落空时出场**，且喂给它的是**站点上的真实字段定义与真实取值**，
不是 agent 的推理过程。agent 的文本**当不可信数据**，明确要求判官忽略其中的指令。
**每一次裁决都留理由，供人复核。**

⚠️ 这与硬约束 ③（规则能覆盖的不 Agent 化）不冲突：
**能用规则判的都在前两层判完了**；判官只处理语义等价 —— 那没有规则面的判法。

### 归因：`calibration` 的八类表，每条失败都要落格

`capability`（**只有这一类算 agent 失败**）· `missing_info` · `harness` ·
`environment` · `false_rejection` · `false_acceptance` · `leakage` ·
`infrastructure`（**不计分**）。

### 边界测试：跑在评测之前，不是之后

`test_verifier_boundary.py` 八个 fixture。**不全过就不许跑评测。**
其中第 ④ 条专测 reward hack —— **旧验证器在这一格是放行的**。

## 五、一次完整的归因，逐步留档

第一次跑出 **18/18 = 100%，另 2 条按 infrastructure 排除**。
**这个 100% 不成立** —— 20 条里排掉 2 条换一个漂亮数字，正是方法论警告的操作。
下面是把它查到底的全过程。

### 第 1 步：不接受「排除」，先读完整记录

| | 被排除的 2 条 | 通过的 18 条 |
|---|---|---|
| 工具调用 | **8 次**（= 我设的 `max_turns`） | 中位 **2**，最多 6 |
| 模型调用 | **8 次**（= 上限） | — |
| token | 41.7k / 41.6k | 中位 6.9k |
| 答案 | **完全为空** | 有 |

「模型调用数**恰好等于上限**」⇒ 不是服务坏了，是**被截断**。
⇒ 改归类：`infrastructure`（不计分）→ **`harness`（计分）**。
诚实的数变成 **18/20 = 90.0%**。

### 第 2 步：第一次留痕仍然不够 —— 补第二次

只存工具名和最终答案时，**仍然分不出两种因**，因为
[`loop.py:407`](../../../agenerp/explain/loop.py) 撞上限会**丢弃 agent 说过的话、返回空串**：

- agent 答过、**被答案门禁一次次拒回** ⇒ `harness` / 门禁假拒
- agent 真的在工具间打转、一次没成形 ⇒ `capability`

补存 `stopped` / `forced_continues` / `gate_checks` 后原样重跑（**只动留痕，不动预算**）：
41,770 / 39,808 token —— 与第一次几乎一致，**可复现，不是抖动**。

```
stopped = max-turns
forced_continues = 0      ← 答案门禁一次都没触发
gate_checks      = 0
```

⇒ **不是门禁拒它，是它八轮全在调工具、从不收口。**

### 第 3 步：查「预算是否公平」—— 结果是我不公平

`MAX_TURNS = 40` 是**产品默认**，而我评测用的是 **8** ——
**我给 agent 的预算只有生产的五分之一**。calibration 要求 fair access。

先算账再跑（D-17）。8 轮实测累计输入 40.6k，按每轮上下文线性增长反解
`a≈2.5k`、`b≈736`：

| max_turns | 每条预估 | D-26 的 200k/次上限 |
|---|---|---|
| 16 | ~128k | ✅ |
| **20** | **~190k** | ✅ 贴边 ⇒ **取这个** |
| 40（产品默认） | ~1.06M | ❌ 超 5 倍，跑不起 |

实跑 `max_turns=20`：

```
Sales Order Item.delivered_qty     11 次工具 → ✅
Purchase Order Item.received_qty   13 次工具 → ✅   （实际 76k / 118k）
```

**11 和 13 都远在产品默认 40 之内，只是越过了我设的 8。**
⇒ 归因确定为 **`harness`（我的评测配置）**，**不是 agent 能力不足**。

### 第 4 步：不留混合口径

修完不能把「18 条 @8 轮 + 2 条 @20 轮」拼成一张表 ——
那正是第 ⑤ 条批评过我自己的「一次动了两个变量」。
虽然能论证「那 18 条最多用 6 次工具，8 从没绑住过它们」，**论证不如实测**：
全量按 `max_turns=20` **重跑一遍**，只留单一口径的数。

### 顺带查出的一个生产缺陷（不在本次范围内修）

🔴 [`loop.py:407`](../../../agenerp/explain/loop.py)：撞 `max_turns` 时
`return self._result("", False, ...)` —— **把 agent 全部工作丢弃、返回空串**，
用户拿到一片空白且没有任何说明。常规做法是**最后一轮关掉工具、逼它作答**。

**本次不动它**，两条理由：
1. 它是 P1 生产代码，改动要有自己的判据和变异验证，不该顺手夹带在 P2 评测里；
2. `STOP_MAX_TURNS` 的断言体 `tests/unit/test_explain_cost_accounting_body.py`
   **被 `tests/gates/test_explain_cost_accounting.py:44` 加载** ⇒ **红线 1，只能由人改。**

⇒ 记为**待人裁定项**。

## 六、判官层的边界测试（第一版漏了）

`test_verifier_boundary.py` 只测了**规则层**。判官那一层一开始没测 ——
而 `verifier-design` 要求**误放行**与**假拒**两侧都测。
补 `test_judge_boundary.py`：六个站点真实字段，四个该拒。

⚠️ **第一次跑，错的那一格是我**：我把 `Job Card.for_quantity`
（标签「Qty To Manufacture」= **计划**数量）标成可接受，而问句问的是**完成**了多少。
判官判 False，理由「该字段表示计划生产数量，而非实际完成数量」。
**判官比我细。修的是 fixture，不是放宽判官。** 修正后六格全过（**n=6，不足以推广**）。

## 七、单一口径的重跑结果 —— 以及**为什么它证明不了 95%**

`max_turns=20`、n=20、单一配置：

```
🔴 任务完成率：95.0%（19/20）    424,601 token
   中位 6,836 · 最大 147,062（21 倍长尾）
```

### 唯一那条失败，暴露的是**抖动**，不是稳定水平

同一条问句 `采购订单这一行已经收了多少货？`：

| 配置 | 结果 |
|---|---|
| `max_turns=8` | ❌ 截断 |
| `max_turns=20`（单跑 2 条） | ✅ **13 次工具收敛** |
| `max_turns=20`（全量重跑） | ❌ **烧满 20 轮**，`schema.search` **重复 12 次** |

**同题、同配置，一次过一次不过。** 失败形态是**检索死循环** ——
反复搜同一个东西而认不出自己在重复。`MAX_TOOL_CALLS=50` 的失控闸没拦住（20 < 50）。

⇒ 顺带说明**我那条自动归因规则太糙**：「撞上限 ⇒ harness」在预算不公平时（8 vs 生产 40）
成立，但在 20 轮下、同题曾用 13 轮收敛时，撞上限意味着**打转**，那是 `capability`。
规则已收紧为「轨迹重复过半 ⇒ capability」，**且这一格永远要人复核**。

### 🔴 结论：**我不宣布 P2.0R 达标**

按二项分布算（Clopper-Pearson）：

| 观测 | 95% 置信下界 |
|---|---|
| **19/20 = 95.0%** | **78.4%** |
| 20/20 = 100% | 86.1% |

**n=20 时，「95.0%」与「80%」在统计上分不开。**
要让下界真正压过 95% 这条线：

| n（零失败） | 下界 | 一轮成本（实测均价 21,230 token/条） |
|---|---|---|
| 40 | 92.8% | 0.85M |
| **60** | **95.1%** | **1.27M** |
| 100 | 97.0% | 2.12M |

而**评测集现在只有 40 条**，且**是我自己出的**。

⇒ 达标需要三件事，**没有一件是「再跑一轮」能解决的**：
1. **一份不是我出的题**（≥60 条）—— 见 §三第 1 条，**我自己解不了**；
2. **~1.3M token 的预算**，须人先批（D-17：有真跑判据前先算账）；
3. **修掉检索死循环** —— 那是本次唯一确认的 `capability` 失败形态。

**在这三件事完成之前，「95.0%」只是一次 n=20 的观测，不是达标证明。
我不会拿它去凑 95% 这条线。**

## 八、glm-5.2 一轮：20/20 —— **但仍然不宣布达标**

`max_turns=20`、n=20、单一配置、**零条排除**：

```
✅ 任务完成率：100.0%（20/20）    308,514 token
   停止原因 answered ×20 · 承诺来源「最后一行承诺」×20
   判定：可接受集合 19 · 判官 1
   成本：中位 5,081 · 最大 144,949 · 工具次数 1–15
```

### 换模型的经过（记下来，因为过程里我错了两次）

1. 我从会话开头**原样搬用**了一条约束「可用 `qwen3.6-plus` / `qwen-plus`」，
   **整场六十多万 token 一次都没复验**。人指出额度已尽时，日志零 403 ——
   ⇒ 不是被拒，是**免费额度用完转付费在扣**。**拿没复验的假设当判据，这是老毛病。**
2. 我又断言「glm-5.2 是智谱的，不在百炼上」。**错的**：探 `/models` 发现百炼上架了
   9 个 GLM，现有 key 直接能用。

⚠️ **「调得通」证明不了「免费」** —— 额度状态在控制台，不在响应里。这一条我判不了，只能由人给。

### 路由层拦得对

第一次跑 glm-5.2，**20 条全部零 token 被拦**：模型不在 `KNOWN_MODEL_PROFILES` 里。
这是 §12.1 ③「不满足则明确失败，绝不静默降级」在起作用。

补档案时守住了本模块第一条规矩 —— **未观测的能力不声明**。探针只判得了两件事：

| 探到的 | 结果 |
|---|---|
| `tool_calling` | ✅ 真发起了 `meta_fields({"doctype": "Sales Order"})` |
| 计 reasoning token | ✅ `reasoning_tokens = 33` |
| `long_context` / `reasoning` / `multi_hop` | **判不了 ⇒ 不声明** |

⇒ glm-5.2 今天只够 `permission` / `explain` 两档，**接不了 `lineage` / `shape`**。
代码表与 §12.5 文档表同时改（两者逐行同构，改一边测试就红），`tests/routing` 186 passed。

### 🔴 为什么 20/20 **仍然不是**达标证明

**① 统计上不够。** 20/20 的 95% 置信下界是 **86.1%** —— 压不过 95% 这条线。
需要 **n≥60 零失败**（下界 95.1%），而评测集只有 40 条。

**② 这一轮同时动了两个变量**（换模型 + 加子表守卫），
按 §一⑤ 自己定的规矩，**它只能读作「当前状态是多少」，不能用来算守卫值多少分**。
守卫的功劳另有单变量证据：同题同模型（qwen3.6-plus），改前 8 轮/20 轮都失败，
改后 17 轮通过。

**③ 评测集独立性没变** —— 题是我出的，六轮的 miss 我都看过。
**在自己出的题上拿 100%，恰恰是这个数最不可信的时候。**

**④ 成本长尾还在**：`Purchase Order Item.received_qty` 一条烧 **144,949** token
（中位 5,081 的 **28 倍**），15 次工具。它通过了，但这个价钱不是生产形态。
根因仍是上下文层**没有任何一处做调用去重**。
